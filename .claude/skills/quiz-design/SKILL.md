# クイズの出題設計

## この技能が効く理由

クイズの品質は**正解を選ぶ力ではなく、間違いの選択肢を作る力で決まる**。正解は材料から機械的に取れる。難しいのは「もっともらしいが違う」3つを用意することで、ここを手抜きすると問題は一瞬で壊れる。

壊れた出題は「難しい／簡単」ではなく**解答者が作品を知らなくても解けてしまう**という形で現れる。だから設問を評価するときは「自分は解けるか」ではなく「**その作品を全く知らない人が、消去法だけで正解できてしまわないか**」を問う。

## 出題を出す前の4つの検査

新しく作った設問も、AIが作った設問も、出す前にこれを通す。ここは機械で検査できるので、コードに落として自動で弾くのが望ましい。

**1. 正解が一つに定まるか**
「主人公の親友は誰？」で親友が2人いたら壊れている。「第3話のサブタイトルは？」のように、材料の中で一意に決まる形にする。曖昧なら設問ごと捨てる。

**2. ダミーが正解と同じ「見た目の階層」にいるか**
正解が人名なら、ダミーも人名。正解が「1998年」なら、ダミーも4桁の西暦。長さ・字種・粒度を揃える。**一つだけ毛色が違う選択肢は、それだけで答えになってしまう。**

よくある壊れ方：正解だけが妙に長い／正解だけが具体的で他が漠然としている／ダミーだけ英数字が混じる。

**3. 消去法で潰せないか**
選択肢のうち3つが明らかに時代・ジャンル・文脈から外れていたら、それは4択の顔をした1択。ダミーは「実際にありえた」ものから取る。

**4. 答えが問題文に漏れていないか**
「連続テレビ小説『あまちゃん』を放送したのは？」の正解が NHK なら、問題文が答えを言っている。設問文と正解の文字列が重なっていないか機械的に見る。

## ダミー選択肢の作り方

材料をどこから取るかで質が決まる。**同じ作品の中の別の本物**が最良で、外から持ってくるほど質が落ちる。

| 正解の型 | ダミーの取り方 | なぜ |
|---|---|---|
| サブタイトル・台詞・出来事 | **同じ作品の別の回**から | どれも本物なので、うろ覚えでは引っかかる。作品外から取ると文体が浮いて一発で分かる |
| 人名（俳優・脚本家） | 対象作から**年代が20年以上離れた**人 | 「実はその人も出ていた」で誤判定になるのを避ける。近い年代から取ると正解が2つになる事故が起きる |
| 数値（年・話数・視聴率） | 正解の前後に散らす | 一定の幅で散らす。正解だけがキリの良い数字にならないよう注意 |
| 固有の分類（放送局など） | 主要なものを並べた固定リストから | 見知らぬ選択肢を混ぜると、知らない=不正解と推測されてしまう |

**正解の位置は必ずシャッフルする。** 生成順のまま並べると正解が特定の位置に偏り、数問で気づかれる。

## 難易度は「層」で持つ

全問を同じ重さにすると、詳しい人と何となく知っている人の差が出ない。**材料の深さで層を分け、深い層ほど配点を重くする**と、点数がそのまま「どれだけ細部を知っているか」になる。

層の分け方の目安：

- **浅い層** — 作品の外側から分かること（放送局、放送年、主演）。知らなくても推測が効く
- **中間層** — 作品を追っていれば分かること（脚本、主要な配役、原作）
- **深い層** — 実際に観ていないと出てこないこと（第N話のサブタイトル、視聴率、細かい出来事）

深い層の問題が作れないなら、その作品では**深さを問える材料が無い**ということ。無理に浅い問題を深い層に格上げしない。配点だけ重くしても難しくはならず、点数の意味が壊れるだけ。

**同じ材料を問う設問を並べない。** 系統ごとに1問までに絞る。「第3話のサブタイトルは？」「第5話のサブタイトルは？」が並ぶと、問題数の水増しに見える。

## 材料が足りないときは、黙って見送る

出題テンプレートは「材料が揃わなければ何も返さない」形にする。**足りない材料を埋めて無理に出題すると、答えが定まらない問題が混ざる。** 一部のテンプレが見送られても、残りで数が揃えば出題は成立する。

そのうえで、**必要な問数に届かなければ止めて、何が取れて何が取れなかったかを解答者に見せる**。黙って質の低い問題で埋めるより、作れなかったと言うほうが良い。

## 地の文から作る（AIを使わずに中身を問う）

表や箱書きから作る出題は、そこに載っている事実しか問えない。だが**中身を問うのに必ずAIが要るわけではない**。あらすじや人物紹介の「地の文」そのものが材料になる。AIを呼ぶ前に、まずこの3つを試すこと。**無料で、何度でも動き、幻覚も起きない**（元の文がそのまま根拠になる）。

**1. 説明文から名前を当てる**
人物紹介の一行（「本作の主人公。北三陸で海女を目指す」）を見せて、誰の説明かを問う。ダミーは同じ作品の別の人物。作品を知らないと答えられない良問になる。
注意：説明文に本人の名前が入っていたら、それは答えが書いてある。出す前に弾く。

**2. 関係を問う**
説明文によくある「◯◯の母」「◯◯の同級生」を拾って、「◯◯の母は誰か」と裏返す。**◯◯がその作品の別の人物として実在することを確かめてから**出す。実在しない相手を指す設問は答えが定まらない。

**3. 地の文の空欄補充**
あらすじの一文から名前を伏せ、何が入るかを問う。元の文がそのまま根拠なので、解説にも使える。
**その文に出てくる人物がちょうど一人のときだけ使う。** 二人以上いると、伏せた先が一意に決まらない。

### 呼び名の揺れに必ずつまずく

日本語の記事は、人物紹介で「天野アキ」と書き、本文では「アキ」と書く。**フルネームだけで本文を探すと、一度も当たらない。** 地の文を使う出題は、ここで必ず一度失敗する。

呼び名の候補（フルネーム、姓、名）を並べ、**その呼び名を含む人物が一人だけのものだけを使う**。「天野アキ」「天野春子」「天野夏」がいる作品では「天野」は誰にも当てられないので捨てる。「アキ」「春子」は使える。

伏せるときは**長い呼び名から先に**。「アキ」を先に伏せると「天野アキ」が壊れて「天野〇〇〇」になる。

## AIに問題を作らせるとき

**先に費用の形を決めること。** 遊ぶたびにAIを呼ぶ作りは、遊ばれた回数だけ課金される。誰かに配るものなら、鍵を埋め込めば自分の請求になり、鍵を入れさせれば遊ぶ人の負担になる。どちらも嫌なら選択肢は2つ:

- **上の「地の文から作る」で済ませる。** 中身を問う目的の多くはこれで足りる
- **作り置きにする。** 開発時に一度だけAIに作らせ、できた設問をファイルに焼き込む。遊ぶ人は0円で、鍵も要らない

それでも実行時にAIを呼ぶ理由があるとき（毎回違う問題を出したい、対象が無数にある）だけ、下を読むこと。

外部データからテンプレートで作る方式は、材料が構造化されている範囲（表・箱書き）しか問えない。**あらすじや人物関係のような文章の中身を問うには、AIに読ませて作らせるのが向いている。** ただしAIの出力はそのまま信じない。

要点は3つ：

1. **構造化出力（`output_config.format` の JSON Schema）で受け取る。** 自由文を正規表現で切り出す作りは必ず壊れる。
2. **受け取った後、上の「4つの検査」を機械で通してから出す。** 検査に落ちた設問は捨て、残りで数を揃える。AIは指示を守るがゼロではない。
3. **根拠を一緒に出させる。** 各設問に「元記事のどこから作ったか」を書かせると、幻覚が目に見えて減り、解答後の解説にもそのまま使える。

プロンプトの組み立て方、JSON Schema の形、検証の落とし方は `references/ai-generation.md` に置いた。AIに出題させる実装をするなら、書き始める前にそれを読むこと。

## 採点と称号

得点は**実際に出した問題の重みの合計**を満点にする。出題数が作品によって変わるので、固定の満点を置くと「20点満点なのに18点しか取れない」事故になる。

称号は得点率で切る。ただし**最高位を100%だけに割り当てると、ほとんどの人が2番目の称号で頭打ちになる**。上から2番目を85%前後に置いて、そこに届く手ざわりを作る。層ごとの正答率も一緒に出すと「どこが弱いか」が分かり、もう一度やる動機になる。

## 検算スクリプト

`scripts/check-questions.mjs` に、上の4検査を機械で回すチェッカーを置いた。設問の配列を JSON で渡すと、壊れている設問とその理由を並べて返す。

```
node scripts/check-questions.mjs questions.json
```

期待する形は `{ text, choices: [4つ], answer, level }` の配列。実装がこの形と違うなら、スクリプト側ではなく呼び出す側で形を合わせる。出題ロジックのテストにも、AI出力の実行時検証にも同じ基準を使うのが要点で、**基準が2箇所に分かれると必ず食い違う**。
