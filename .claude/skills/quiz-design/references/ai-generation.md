# AIに問題を作らせる

テンプレート方式では、構造化された材料（表・箱書き）にある事実しか問えない。あらすじ・人物関係・出来事のような**文章の中身**を問うには、原文をAIに読ませて作らせる。この文書はその実装のための覚書。

## 目次

1. 全体の流れ
2. 何を渡すか（入力を絞る）
3. JSON Schema で受け取る
4. リクエストの形（ブラウザから直接呼ぶ場合を含む）
5. 受け取った後の検証
6. 費用の見積もりと表示
7. よくある失敗

## 1. 全体の流れ

```
原文を取ってくる → 必要な部分だけ抜く → AIに設問を作らせる（構造化出力）
  → 機械で検証して壊れた設問を捨てる → 足りなければテンプレート出題で埋める
```

**AI出題とテンプレート出題は置き換えではなく、重ねる。** AIは中身を問えるが、通信・費用・失敗の可能性がある。テンプレートは確実だが浅い。両方を持って、AIが使えないときはテンプレートだけで成立する形にしておくと、鍵を持っていない人でも遊べる。

## 2. 何を渡すか（入力を絞る）

記事全文をそのまま投げると、**費用がそのまま記事の長さに比例する**。日本語はおおむね1文字1トークン前後なので、3万文字の記事は約3万トークン、入力だけで安くはない。

必要な節だけ抜く。クイズに使えるのは「あらすじ」「登場人物」「各話」あたりで、「受賞」「関連商品」「外部リンク」は要らない。抜いたうえで上限文字数で切る。切るときは**節の途中で切らない**（文の途中で切れた材料から作られた設問は壊れる）。

材料は一度だけ取って使い回す。同じ作品でもう一度遊ぶたびに呼び直すと、費用が回数分かかる。

## 3. JSON Schema で受け取る

自由文で返させて正規表現で切り出す作りは必ず壊れる。`output_config.format` に JSON Schema を渡すと、返り値が必ずその形になる。

```js
output_config: {
  format: {
    type: "json_schema",
    schema: {
      type: "object",
      properties: {
        questions: {
          type: "array",
          items: {
            type: "object",
            properties: {
              text:    { type: "string" },
              choices: { type: "array", items: { type: "string" } },
              answer:  { type: "string" },
              level:   { type: "integer" },
              why:     { type: "string" },
              source:  { type: "string" }
            },
            required: ["text", "choices", "answer", "level", "why", "source"],
            additionalProperties: false
          }
        }
      },
      required: ["questions"],
      additionalProperties: false
    }
  }
}
```

`source` は「元原文のどこから作ったか」。**これを required にしておくと幻覚が目に見えて減る**（根拠を書けない設問は作りにくくなる）。解答後の解説にもそのまま使える。

`answer` は選択肢の**文字列そのもの**にする。添字（0〜3）で返させると、シャッフルしたときに対応が壊れやすい。

Schema は返り値の**形**しか保証しない。中身の質は保証しないので、検証は別に要る（5節）。

## 4. リクエストの形

エンドポイントは `POST https://api.anthropic.com/v1/messages`。必須ヘッダは `x-api-key`、`anthropic-version: 2023-06-01`、`content-type: application/json`。

モデルは `claude-opus-5` を既定にする。より安く速くしたいときは `claude-sonnet-5`、`claude-haiku-4-5` があるが、**どれを使うかは作る側が勝手に下げず、使う人に選ばせる**。

`output_config.effort` は既定が `high`。ブラウザで人が待つ画面では待ち時間が体感に直結するので、`medium` から始めて、出題の質が落ちるようなら上げる。

### ブラウザから直接呼ぶ場合

`anthropic-dangerous-direct-browser-access: true` を付けると CORS が通る（公式SDKも `dangerouslyAllowBrowser: true` のときこのヘッダを送っている）。

**これはAPIキーがブラウザに載るということで、危険な名前は正確な警告。** 成立するのは「**遊ぶ人が自分のキーを入れて、自分の分だけ課金される**」形に限る。守ること：

- キーはリポジトリに置かない。画面から入力させ、その端末の中（`localStorage`）にだけ置く
- 入力欄は `type="password"`。画面に平文で出さない
- 「キーは端末内にだけ保存され、Anthropic以外には送らない」と画面に明記する
- 消す手段を用意する

作った人のキーを埋め込んで配ると、**他人の遊んだ分が全部自分の請求になる**。それをやるならサーバー側で受けるしかなく、その時点で「1枚のHTML」ではなくなる。

### 公式SDKを使わない判断について

ビルド無しの1枚HTMLでは npm パッケージを置く場所が無い。CDN からの ESM 読み込みも選べるが、第三者CDNへの実行時依存が増え、`file://` で開いたときに動かないことがある。**「1枚のHTMLで動く」が売りのアプリでは、素の `fetch` を選んでよい。** その代わり、上のヘッダを自分で正しく付ける責任は自分で持つ。

## 5. 受け取った後の検証

Schema を通っても、中身は壊れていることがある。SKILL.md の4検査を必ずコードで通す。実装では最低限これを見る：

- `choices` がちょうど4つで、重複が無い
- `answer` が `choices` の中に**文字列として存在する**（表記ゆれで一致しない事故が多い）
- `level` が想定の範囲
- `text` の中に `answer` が含まれていない（答えの漏れ）
- 選択肢の長さが極端に偏っていない（正解だけ長い、を弾く）

落ちた設問は**捨てる**。直そうとしない。足りない分はテンプレート出題で埋めるか、問数を減らして「作れた分だけ」と正直に出す。

検証は SKILL.md の `scripts/check-questions.mjs` と同じ基準にする。テストと実行時で基準が分かれると必ず食い違う。

## 6. 費用の見積もりと表示

呼ぶ前に概算を、呼んだ後に実績を出す。返り値の `usage.input_tokens` / `usage.output_tokens` と単価を掛ければ実額が出る。

**使う人が自分のキーで払うなら、いくらかかったかを画面に出すのは礼儀。** 見えないまま課金される作りにしない。

単価はモデルごとに違い、変わる。コードに直接埋めず、モデルごとの表に持って、出典（公式の価格ページ）を近くに書いておく。

## 7. よくある失敗

| 失敗 | 直し方 |
|---|---|
| 記事全文を毎回投げて費用が跳ねる | 節を絞って上限で切る。材料は一度取って使い回す |
| `answer` を添字で返させて対応が壊れる | 文字列で返させる |
| AIの設問をそのまま出して、答えが2つある問題が混ざる | 4検査を通して落ちた設問を捨てる |
| 通信に失敗すると何も出せない | テンプレート出題を残し、AIが使えないときはそれだけで成立させる |
| 「作れませんでした」だけ出て原因が分からない | 何が取れて何が取れなかったかを画面に出す |
| キーを埋め込んで配布し、他人の分が自分の請求になる | 使う人が自分のキーを入れる形にする |
