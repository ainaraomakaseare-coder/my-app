# おもいでバインダー iOS / TestFlight

このフォルダはルートの`omoide.html`をCapacitorでiOSアプリに包み、GitHub ActionsのmacOS runnerからTestFlightへアップロードする設定です。画面・クイズ・Supabase接続先は`omoide.html`が正本です。

## TestFlightビルド前の準備

1. Supabase SQL Editorで[`database/community-quiz.sql`](../database/community-quiz.sql)、続けて[`database/community-members.sql`](../database/community-members.sql)を実行します。後者は参加権限を必須化し、`photos`バケット全体をPrivateに変更します。既存Web版も新しいHTMLへ切り替える必要があります。既存の人物データは全項目共有として扱われます。実行前にDBのバックアップと既存バケットの利用先を確認してください。
2. Supabase Authで匿名サインインが有効になっていることを確認します。
3. Apple DeveloperでBundle ID `com.hiroyaapps.omoidebinder` を登録し、そのID用のApp Store Connect配布用プロビジョニングプロファイルを作成します。名前は`omoide-binder-appstore`にします。
4. App Store ConnectにiOSアプリ「おもいでバインダー」を作成します。
5. GitHub Actions secretsに、このアプリ固有の`OMOIDEBINDER_IOS_PROVISIONING_PROFILE_BASE64`を登録します。配布証明書、証明書パスワード、Apple Team ID、App Store Connect APIキーは既存の旅の足跡／おもいでWiki用の共有secretsを使います。
6. GitHubのActionsから「おもいでバインダー iOS ビルド & TestFlightアップロード」を手動実行します。署名やApple側の登録に未設定があると失敗します。成功後、App Store ConnectのTestFlightで内部または外部テストグループにビルドを割り当てます。

`omoide-binder-ios-build.yml`は既存のWiki用workflowを土台にしていますが、Bundle IDとプロビジョニングプロファイルは別です。既存Wikiのプロファイルを流用しないでください。

架空エピソードの出題には、上記2つのSQLの後に[`database/community-fiction.sql`](../database/community-fiction.sql)も実行します。プロフィールとは別の、ルーム単位の架空問題テーブルを追加します。このSQLも本番には未適用です。

## 名簿の一括登録

「入力テンプレート」でTSVを保存し、Numbers・Excel・Google Sheetsなどで1人1行に編集して「名簿から一括追加」から読み込みます。`tags`と`hobbies`は`;`区切り、`episodes`は1人1件の自由記述です。`share_name`などの`share_`列は`true` / `false`で共有項目を選べます。写真は名簿には含めず、追加後にプロフィールからアップロードします。一度に500人までです。

参加中のメンバーは全員、一括登録とプロフィール編集を使えます。参加アカウントの退出・招待コード変更は管理者だけが行えます。

## 管理者と参加者の退出

新しいコミュニティを作った参加者が管理者です。「参加者を管理」から、名前・参加日・ID末尾を確認して「退出させる」を選びます。確認後、参加権限の停止と招待コードの変更を1つのDB処理で行います。新しいコードを新規参加者に共有してください。既存の参加者はそのまま利用できます。

招待が広まって知らない人が入ってきた場合は、「新しい参加を一時停止」を選びます。招待コードを無効にし、新しい参加をサーバー側で停止します。既存のメンバーは利用を続けられるので、参加者一覧を見ながら必要な人を退出させます。停止中に退出やコード変更を行っても、受付が勝手に再開することはありません。

再開するときは「新しいコードで参加を再開」を選び、発行された新しいコードを参加してほしい人に共有します。停止前や停止中のコードは再開後も使えません。アプリ本体のURLや全員のアカウントを変更する操作は不要です。参加受付の停止・再開も管理者限定です。通信エラー時は現在の受付状態を再取得し、結果を確認できない場合は操作を成功扱いにしません。

- 退出対象はログイン中の参加アカウントです。名簿のプロフィールとは別です。既存のプロフィール・エピソードは残し、その人のランキング記録は削除します。
- 一般参加者からの管理操作、自分自身の退出、別の管理者の退出はサーバー側でも拒否します。
- 退出済みIDは新しい招待コードを知っても再参加できません。別端末で新しいIDを作っても、誤送信された古いコードは使えません。新しいコードを別アカウントに再共有すれば、そのアカウントは参加できるため、人間本人を恒久的に識別するBANではありません。
- 人物・所属ノート・ランキング・写真は、毎回DB/Storageで参加権限を確認します。画面は12秒ごととアプリ復帰時に確認し、権限を失うと表示データと写真のメモリを消去します。取得済みファイル・スクリーンショット・端末やCDNの既存キャッシュは回収できません。
- 匿名認証の既存セッションを再利用します。管理者端末のアプリ削除・ストレージ消去後の復旧は、SQL Editorで信頼できる新しい参加者IDへ管理者権限を割り当てて行います。メール認証によるアカウント復旧は未実装です。

## 既存ルームの管理者を指定する

移行直後、既存ルームは管理者を指定するまでアクセスできません。先着者を自動で管理者にしないためです。アプリの参加画面で「管理者に伝える参加者ID」を開き、運営本人のUUIDを確認します。新しい管理者端末でアプリを開いた状態で、Supabase SQL Editorから実行します。UUIDやルームIDを他人から無検証で受け取って使わないでください。

```sql
-- 既存ルームを確認（旧合言葉のSHA-256も、このIDに対応します）。
select id, name from public.binder_rooms;

-- 下の2つの値を、対象ルームと運営本人の参加者IDに置き換えます。
insert into public.binder_members(room_id, user_id, display_name, role, status)
values ('対象ルームのID', '運営本人のUUID'::uuid, '管理者', 'admin', 'active')
on conflict (room_id, user_id) do update
set role = 'admin', status = 'active', removed_at = null;
```

アプリを再読み込みすると参加済みのルームに戻れます。「参加者を管理」→「新しいコードで参加を再開」で初回コードを発行してください。以前の`houken`は新しい招待コードとして使いません。旧人物データは元のルームIDのまま残ります。

## クイズ

「覚える区分を選ぶ」で、プロフィールの所属（放送研究会・大学・バイト先など）を複数選択できます。チェックを外した区分は今回の学習対象から外れ、正解候補・4択の他の選択肢も選択した区分内に限定します。対象が4人未満など出題条件を満たさない場合は、区分を追加する案内を表示します。自動で他の区分へ広げることはありません。

各区分と選択範囲全体に「覚えた人数／名前を共有している対象人数」を表示します。複数の区分にいる同じ人は、選択範囲全体で1人として数えます。共有されていない所属の名称は表示せず、「区分の共有なし」に含めます。学習対象から外してもプロフィールや正解記録は削除しません。

選択はコミュニティと参加者IDごとに端末へ保存します。初期状態はすべての区分が対象です。「すべて外す」は対象なしとして保存し、勝手に全員へ戻しません。クイズの途中で区分を変える場合は確認し、進行中の出題を終了します。それまでの正解記録は残ります。ランキングはコミュニティ全体の累計です。

- 写真・特徴は人名4択、エピソードは人名4択＋「そんな人いない」です。明示的に架空として保存した問題だけ「そんな人いない」を正解にします。登録された話と同じ文の架空問題は出題から外します。
- 「この人のエピソードは？」は、共有された写真と名前（写真が非共有なら名前のみ）を出し、登録エピソードの4択から選びます。選択肢は同じ学習区分の別人の話から取ります。本人の別の話、複数人に共通する話、名前で答えが分かる話、非共有の話は誤答候補にしません。4人分の材料がなければ追加案内を出します。
- 「おまかせ」は写真・特徴・人からエピソード・エピソードから人・○×を順番に混ぜて最大10問出します。材料が揃えば両方向を含め、同じエピソードを向きを変えて二重出題しません。人からエピソードを正しく当てた場合も、その人物を覚えた人数に1人として加算します。
- 「エピソード○×」は、共有されたプロフィールのエピソードを○、架空問題テーブルの話を×として出題します。登録内容を基準としたクイズであり、未登録だから架空と判定したり、文章の内容から自動で真偽を推測したりしません。○×は1件から遊べます。
- 選択した共有項目に材料があり、正解の名前が一意で、別の3人をダミーにできるときだけ出題します。条件が揃わない問題は出しません。
- 同じ友達を複数回正解しても「覚えた友達」は1人として数えます。ランキングはルーム内で覚えた人数順です。
- 問題生成はアプリ内の登録情報だけを使い、AI呼び出しや追加API料金はありません。

「架空のエピソードを出題用に追加」で本文と区分を指定し、架空であることを確認して保存できます。参加者は追加でき、削除できるのは投稿者本人と管理者です。退出者や別ルームの参加者は取得・追加できません。問題は選んだ区分から出題し、プロフィールへ書き込みません。人名問題は正解候補を含め4人以上が必要で、架空の話でも区分外から選択肢を補いません。

ユーザー指定の「ゲノムが恵比寿で待った話」「エンゼルスと呼ばれる話」は、どちらも×の例文です。「架空の例題2問を試す」ならそのまま遊べますが、正解数やランキングには保存しません。コミュニティで使う場合は例文ボタンで入力し、区分を選んで架空問題として追加してください。

通常出題の○×と「そんな人いない」の正解は正解数に加えますが、人物を特定したわけではないため「覚えた人数」は増えません。実際の人物を当てた問題だけ人数に加算します。

## 共有項目とプライバシーの制限

共有項目はアプリの一覧・詳細・クイズで表示する項目を選ぶ設定です。`community-members.sql`適用後は、ルームごとの参加権限がRLSで検査され、写真はPrivate Storageから認証付きで取得します。新しい写真は`ルームID/参加者ID/ファイル名`へ保存します。旧写真は移行時に元のルームとの対応を固定します。保存値のURLには`/public/`が含まれる場合がありますが、表示にはそのURLを直接使わず、認証付き取得で作った端末内の一時URLを使います。

ただし、項目単位の非公開はDB側の秘匿ではありません。同じルームの参加者はAPI経由で保存項目を取得・編集できます。本人/登録者ごとの所有権と項目別のサーバー側非公開は未実装です。本番Supabaseへの移行はこの作業では実行していません。TestFlightではまず架空データで移行後の動作を確認してください。

## ローカル検証

`database/tests`で`npm ci`、`npm test`を実行します。PGliteのPostgreSQLエンジンで実際のSQLを適用し、管理者限定RPC・退出後の読み書き拒否・旧招待コード無効化・受付停止中の参加拒否・停止を維持した退出・新コードでの再開・他ルーム分離・旧写真の権限・再適用を検証します。画面スクリプトもDOM環境で、確認のキャンセル・退出・データ消去・遅れて返る取得結果・セッション復元・受付停止/再開・通信失敗を検証します。SupabaseのHTTP API・CDN・iPhone実機検証の代わりにはなりません。

区分別クイズでは、選択区分だけの4択、複数区分の重複除去、区分別の進捗、対象不足時の案内、端末保存と別参加者への設定非適用、途中変更の確認を検証します。

エピソード問題では「そんな人いない」の正誤、架空問題による人数の水増し防止、○×、指定例題2問の×判定と記録非保存、区分・重複文の除外、プロフィールと架空問題の保存先の分離、架空問題のRLSを検証します。

人からエピソードを当てる問題では、区分内の4択・一意の正解・人物への人数加算・材料不足時の案内・おまかせの両方向出題と同一話の重複除去を検証します。

実装根拠: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)、[Storage access control](https://supabase.com/docs/guides/storage/security/access-control)。

## iOSでの準備

`npm run prepare:ios`がルートの`omoide.html`を`www/index.html`へコピーし、Capacitorがそれをアプリに同梱します。ローカル画面の`iosScheme`は標準の`capacitor`です。WKWebViewが処理する`http`や`https`は指定できません（[Capacitor設定](https://capacitorjs.com/docs/config)）。Supabaseへの通信はHTTPSのままです。GitHub ActionsはiOSプロジェクトを毎回生成し、ネイティブ`ios/`フォルダをGitに保存しません。

## クイズの難易度
初級は写真から名前の4択、中級は各形式の4択と○×、上級は対象全員の人名選択と「そんな人いない」です。人物からエピソードを選ぶ問題は中級・上級とも4択です。
本番接続前に database/community-quiz-levels.sql を既存のクイズ・メンバー用SQLの後に実行してください。level_scores にレベル別成績を保存し、ランキングもレベル別に表示します。導入前の記録は総合成績のみ残ります。サンプル確認版には追加SQLは不要です。
