## 実施作業

**1. 出題設計を Skill として書き出した**（`.claude/skills/quiz-design/`）

クイズの良し悪しをどう判断するかを文章にしました。芯は「**クイズの質は、正解ではなく間違いの選択肢で決まる**」ということ。出題を出す前の4つの検査（正解が一意か／ダミーが正解と同じ見た目の階層か／消去法で潰せないか／答えが問題文に漏れていないか）と、ダミーの取り方、難易度の層の持ち方、AIに問題を作らせるときの作法を書いています。検査を機械で回すスクリプトも付けました。

**2. その Skill をドラマ王に当てた**

当てた結果、自分で作ったアプリの中から2つ見つかりました。

- **同じ言い回しの設問が4問並んでいた。** 「『あまちゃん』で ○○ を演じたのは？」が結果画面に4つ。README には「系統ごとに1問まで」と書いてあったのに、コードは1テンプレから4問作れる状態でした。書いたつもりと実物がずれていた
- **結果画面の内訳の帯が、一度も伸びていなかった。** `span` のままで `height` が効かず、ずっと空の帯を出していた。気づいていませんでした

**3. AIに問題を作らせる仕組みを作り、そして取りやめた**

DAY5 の時点では、記事の表と箱書きにある事実しか問えませんでした。「誰が何を演じたか」は問えても「物語の中で何が起きたか」は問えない。そこで一度は、記事の文章を Claude API に読ませて中身を問う設問を作らせる形を実装しました。動きましたし、テストも通りました。

**ただしこれは、遊ぶたびに課金される作りでした。** 1回の出題でおよそ $0.12。誰かに配るものでこれをやると、鍵を埋め込めば他人が遊んだぶんが全部自分の請求になり、鍵を入れさせれば遊ぶ人の負担になります。どちらも良くないと判断して、**丸ごと取り下げました**。

**4. AIを呼ばずに、記事の地の文から中身を問う形に作り直した**

やりたかったのは「AIを呼ぶこと」ではなく「物語の中身を問うこと」でした。それは記事の**地の文**（あらすじ・人物紹介）から直接できます。

- **説明文から役名を当てる** —「本作の主人公。東京育ちの内気な女子高生で、北三陸で海女を目指す」と説明されるのは誰か
- **人物の関係を問う** — 説明文の「アキの母」を裏返して「天野アキ の母にあたるのは？」
- **あらすじの空欄補充** — あらすじの一文から名前を伏せて、何が入るかを問う

**0円で、鍵も要らず、どの作品でも、何度遊んでも同じです。** しかも記事の文がそのまま根拠なので、事実を作り出す余地がありません。

## エラー・つまずき

- **作業ブランチの初期位置が古かった。** DAY3（チンチロ）のコミットを指していて、DAY6 で整理した `apps/` の形になっていなかった
- **公式SDKが使えなかった。** Claude の公式SDKは npm パッケージで、ビルド無しの1枚HTMLには置き場所がない（この時点ではまだAPIを呼ぶ設計だった）
- **作ったあとで、課金の形がまずいことに気づいた。** 動くものはできたが、遊ばれた回数だけお金がかかる。配って遊んでもらうアプリでは成立しない
- **記事の呼び名が揺れていて、あらすじの人物を一人も見つけられなかった。** 人物紹介は「天野アキ」、あらすじは「アキ」。フルネームで探すと一度も当たらない
- **自分で書いた検査が、正しい設問を弾いた。** 「正解だけ長さが浮いている」の判定が比率だけを見ていたため、「海女」対「喫茶店の店主」のような日本語では普通の組み合わせまで落としていた。実際にAIが作った良い設問が1問消えていた
- **繰り返しを厳しく禁じたら、今度は問題数が足りなくなった。** 上限をきつくすると、材料の薄い記事で10問に届かない

## 解決方法

- ブランチは `main` から切り直した（`git checkout -B <ブランチ名> origin/main`）
- SDKは使わず、素の `fetch` で API を呼んだ。ブラウザから直接呼ぶのに要るヘッダは、公式SDKの実装を読んで正確な名前を確かめてから自分で付けた
- 長さの判定は、比率だけでなく字数の差も一緒に見るようにした。**Skill 側の検査スクリプトも同じ基準に直した**（基準が2箇所に分かれると必ず食い違うため）
- 上限は「まず変化をつけて採り、足りないときだけ控えから足す」二段構えにした。問題が少ないことと繰り返しに見えることを比べて、少ないほうが困ると判断した
- **AI呼び出しは丸ごと外した。** APIキーの入力欄も費用表示も消し、記事の地の文から作る3種類の出題に置き換えた。実装したものを捨てる判断だが、遊ぶ人にお金がかかる作りを残すよりよい
- 呼び名は、フルネーム・姓・名の候補を並べ、**その呼び名を持つ人物が一人だけのものだけ**を使うようにした。「天野アキ」「天野春子」「天野夏」がいるので「天野」は捨て、「アキ」「春子」を使う。伏せるときは長い呼び名から先に処理する（「アキ」を先に伏せると「天野アキ」が壊れる）

## 今日できるようになったこと

- 判断の基準を Skill として書き出し、次に作るときも同じ基準を効かせる
- 書き出した基準を自分の作ったものに当てて、見えていなかった不具合を見つける
- 記事の文章から、事実だけでなく「物語の中身」を問う問題を組み立てる
- 作ったものを機械で検査し、落ちたぶんは直さず捨てる
- 課金の起きる作りに気づいて、お金のかからない作りに設計し直す
- 動いているものでも、作りがまずければ捨てる判断をする

## 今日の動画で使えるポイント

1. **Skill を当てたら、自分のアプリのバグが2つ出てきた。** 「同じ問題が4回並ぶ」と「グラフが一度も伸びていなかった」。しかも README には正しいことが書いてあって、コードだけがずれていた。**書いたつもりと実物のズレ**が、基準を外に出したことで見えた
2. **AIで作ったものを、動いた状態から捨てた。** 遊ぶたびに $0.12 かかる作りだったから。「動くかどうか」の前に「配れるかどうか」を見る。**AIを使うことが目的ではなかった**、というのが today の一番の学び
3. **やりたかったのは「AIを呼ぶこと」ではなく「物語の中身を問うこと」だった。** それは記事のあらすじから直接できた。あらすじの一文から名前を伏せれば、それだけで良い問題になる。0円で、鍵も要らず、どの作品でも動く
