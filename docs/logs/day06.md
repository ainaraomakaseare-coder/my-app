## 実施作業

### 1. 人狼アプリ

各参加者が自分のスマホで自分の役職だけを見られる人狼アプリを作りました。1台のスマホを回して確認するやり方をやめるのが目的です。

- 親機（GM卓）で参加者の名前と役職の構成を決める
- 部屋を作ると、**全員共通のQR**と**1人ずつの4桁の番号**が出る
- 全員が同じQRを読み（順番待ちなし）、進行役から聞いた自分の番号を入れると、その端末に自分の役職だけが出る
- 1人ずつ個別のQR／リンクを配る方式にも切り替えられる（離れている人にはLINEでリンクを送れる）
- 夜・朝・議論・投票・勝敗判定まで親機が進行する
- 占い師・霊媒師の結果も、その人の端末にQRで渡す
- 役職は村人・人狼・占い師・騎士・霊媒師・狂人から部屋作成時に自由に選べる
- 初日の襲撃なし／騎士の連続ガード禁止を切り替えられる

**仕組み**：サーバーを使いません。役職は URL の `#` より後ろに入れています。`#` より後ろはブラウザからサーバーへ送られないので、どこかに記録が残りません。進行状況は親機のブラウザ（localStorage）に保存され、リロードしても続きから再開できます。

部屋のリンクには全員ぶんの役職が入っていますが、それぞれの4桁の番号から作った鍵で1人ぶんずつ包んであり、**自分の番号でしか開けません**。15万通りの番号を総当たりして、他人の役職が誤って開くケースが0件であることを確認しました。

QRコードの生成は外部ライブラリを使わず自前で実装しました（`apps/day06-jinro/qr.js`）。

## エラー・つまずき

### 新規リポジトリを作れなかった（403）

`docs/progress.md` の片付け手順は「管理リポジトリ `30days-30apps` を作り、アプリごとにリポジトリを分ける」でしたが、作業環境の権限では新規リポジトリを作成できず `403 Resource not accessible by integration` で失敗しました。

### 自作したQRコードが、長いデータだと読めなかった

外部ライブラリを使わずQRコード生成を実装したところ、短いデータは読めるのに**141バイトを超えると全く読めない**という状態になりました。見た目は正しいQRコードに見えるので、目視では気づけませんでした。

原因は**位置合わせパターン（QRの中にある小さい四角）の配置バグ**でした。中心がタイミングパターン（QRの6行目・6列目にある点線）に重なる場合に、「すでに他のパターンが置かれている場所だからスキップ」と誤判定していました。正しくは、スキップしてよいのは位置検出パターン（3隅の大きい四角）と重なる3箇所だけで、タイミングパターンの上には**置くのが正しい**動作でした。

バージョン6以下は位置合わせパターンの中心が2個しかなく、その2個がちょうど3隅にあたるため、たまたま正しい結果になっていました。バージョン7以上で中心が3個以上になった瞬間に露見しました。

### 「進行を全部」と「サーバー無し」が両立しない部分があった

要件を固める段階で、この2つが一部で両立しないことが分かりました。役職・仲間の人狼・占い結果はゲーム開始時に確定しているので各自の端末に配れますが、**襲撃先・護衛先・投票**は複数人の選択を突き合わせないと結果が決まりません。サーバーが無いと、Aさんの端末の選択をBさんの端末に届ける経路がありません。

### GitHub Pages は非公開リポジトリだと有料

無料プランで GitHub Pages を使うには、リポジトリがパブリックである必要がありました。

### 「部屋番号で入る」が、最初は作れないと判断した

「親が部屋を作ると部屋番号が出て、他の人は番号を入れて入る」という要望に対して、最初は「それはサーバーが必要なので今日は無理」と答えました。番号を入力する端末は自分の役職をまだ持っておらず、どこかから取ってくる必要があるからです。

次に「共通QR＋個人コード」を代案として出しましたが、これも**コードを本人にどう伝えるかを詰めていませんでした**。口頭で言えば隣に聞こえ、画面で見せれば全員のコードが見える。1人ずつこっそり見せるなら、結局それまでのQRを1人ずつ見せるのと同じ手間になります。穴が増えるだけだと気づいて、いったん「作らないほうがいい」と引っ込めました。

最終的には、**「他人の役職を覗こうとする人はいないので、そこまでの管理は不要」という判断をもらって**作りました。番号は口頭で伝える前提なので4桁の数字にしています。守るべき秘密の強さを決めるのは作る側ではなく使う側だ、というのが今回の学びです。

### 人間の判断待ちで作業が止まった

AIが要件を確認する質問を投げた時点で、こちらが席にいないと作業がそのまま止まります。今回は公開方法・機能範囲・片付けの進め方など、判断が要る場面が複数回あり、そのたびに待ち時間が発生しました。

「先に質問させる」というルール自体は今回も有効に働いた（サーバー無しと全自動進行が両立しないことを着手前に指摘できた）ので、ルールを変えるのではなく、**質問を受けるタイミングの作り方**が課題です。

### セッションの利用上限で開発が止まった

途中でAI側のセッション利用上限に達し、再開できるまで開発が止まりました。`docs/progress.md` の「まだ配置していないつまずき」に挙がっていた項目ですが、DAY6 で実際に発生しました。

### Playwright のバージョンが環境のブラウザと合わなかった

テスト用に入れた Playwright が、環境に用意されているブラウザより新しいビルドを要求して起動できませんでした。

## 解決方法

- **リポジトリ作成の403**：分割をあきらめ、1つのリポジトリの中で `apps/dayNN-アプリ名/` に分ける形へ切り替えました。将来分割できるようになったとき用に `docs/templates/app-repo-CLAUDE.md` は残してあります
- **QRのバグ**：本物のQRデコーダー（jsqr）で読み返すテストを書き、1〜858バイトの全長で総当たり検証しました。バグ修正後は全て通過。このテストは `apps/day06-jinro/test/qr.test.js` に残してあります
- **両立しない部分**：秘密にすべき情報（役職・仲間・占い結果）は各自の端末、突き合わせが要るもの（襲撃・護衛・投票）は親機、と役割を分けました。この設計上の制約は README にも明記しました
- **Pages が有料**：リポジトリをパブリックにする方法を選びました。公開前に全ブランチをAPIキー混入で検査し、検出なしを確認してから進めました
- **Playwright**：ブラウザをダウンロードし直さず、環境にあるブラウザのパスを直接指定しました
- **判断待ち・セッション上限**：どちらもこの日のうちには解消できませんでした。作業のやり方の問題なので、次回に向けた申し送りとして「時間」の節に残します

## 今日できるようになったこと

- 作ったアプリをインターネットに公開する（GitHub Pages）
- 複数の端末から同じアプリを使う仕組みを作る
- サーバーを使わずに、端末ごとに違う情報を届ける（URLの `#` より後ろを使う）
- 外部ライブラリに頼らず、必要な部品（QRコード生成）を自分で実装する
- 「正しく動いているように見えるが実は壊れている」ものを、本物のデコーダーで機械的に検証する

- どこまで秘密を守るかを、作る側で決めずに使う側に確認する
- 散らかったブランチからファイルを取り出して、置き場所を整理する
- 公開前に秘密情報（APIキー）が混ざっていないか検査する

## 今日の動画で使えるポイント

1. **「見た目は完璧なQRコード」が実は読めなかった話。** 自作したQRコードが、短いデータなら読めるのに141バイトを超えると全く読めませんでした。しかも見た目は本物と区別がつきません。原因はQRの中の小さい四角の置き場所を1箇所間違えていたこと。目で見て確認する方法では絶対に見つからないので、本物のQRリーダーで読み返すテストを書いて総当たりで潰しました。**「動いているように見える」と「動いている」は違う**、が今日いちばんの学びです。

2. **AIに「全部やって」と言ったら「それは無理です」と返ってきた場面。** 「進行を全部やる」「サーバーは使わない」の2つを頼んだら、要件を固める段階で「この2つは一部で両立しません」と指摘が返ってきました。占いの結果は配れるけれど、襲撃先と護衛先の突き合わせはサーバーが無いと届けられない、と。作り始めてから気づいたら大きな手戻りでした。**先に質問させるルールが効いた**回です。

3. **「アプリ5個作ったら、どこに何があるか分からなくなりました」の片付け。** main ブランチが無く、合流していないブランチが4本、しかも1つのリポジトリに3日分のアプリが積み上がっている状態でした。さらに片付けの手順どおりに新しいリポジトリを作ろうとしたら権限が無くて403。**予定した手順が使えなかったので、別のやり方に切り替えて**1つのリポジトリの中で整理しました。移動後に全アプリのテスト1028件を通して、壊れていないことを確認してから古い場所を消しています。

4. **公開＝全世界に見えるということ。** GitHub Pages を無料で使うにはリポジトリを公開する必要があり、公開するということはコードが全部見えるということでした。公開ボタンを押す前に、APIキーや秘密情報が混ざっていないか全ブランチを検査しました。今回は検出なしでしたが、**「公開する」の前にやることがある**と分かった回です。
