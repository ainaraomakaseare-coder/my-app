## 実施作業

### ログイン機能

- 「Googleでのログイン機能作ろうよ」から着手。Google Cloud ConsoleでOAuthクライアントIDを設定する過程で、「これって今後iOSアプリでできるようにする前提はわかっていますか？」という質問を受け、**GoogleがOAuthログインをアプリ内蔵WebViewから行うことをセキュリティ上ブロックしている**ことが判明。CapacitorでWeb版を包むiOSアプリの中では、Googleログイン（Web向けJSライブラリ）が動かない可能性が高いという設計上の見落としだった
- この発見を受け、ユーザーの提案「メールアドレス認証でメールが送られてワンタイムパスワードをいれる形」で、それまでの「その場で入力するだけで検証しない」簡易メールログインを、実際にメールでコード（OTP）を送って照合する方式に置き換え（送信はResend、無料枠3,000通/月）
- 参加者（companions、テキストのみ）とは別に、ログイン中の本人が「参加する」を押すことでアカウントを旅行に紐付けられる「アカウント参加者」を追加。生のメールアドレスではなく6桁のアカウントIDで紐付け、`docs/adr/0001`に設計判断を記録
- マイログに「参加した旅行一覧」を追加（アカウントに紐づき、端末をまたいで同じ内容が見られる）

### 音声認識機能

- 「旅行を振り返るとき、その日にあったことをまとめて音声入力すれば予定に追加してくれる」という要望を`interview-me`で深掘り。以前「要件が固まっていないため見送り」としていた「音声で旅程を作る」機能を、具体例（「ダイヤモンドヘッドに登って、そのあとファーマーズマーケットで…」のような長い語り）を出してもらいながら要件を確定させた
- 確定した要件：今開いている日タブに対して、音声＋URL・店名の雑多なメモを渡すと、AIが話した順番どおりに複数の予定・記録に分割して直接保存する（保存前の確認画面は挟まない、日付はAIに判定させない、評価・費用はAIに作らせない）。`docs/adr/0002`に設計判断を記録
- 実装：**このアプリで初めてAI（OpenAI）を呼び出す機能**。当初は音声を直接AIに聞かせる設計（Responses APIへの音声input）にしたが、実機での動作確認で`"Audio input is not available."`というエラーが判明し、**Whisperで先に文字起こしし、そのテキストを元に予定・記録へ分割する2段階構成**に作り直した
- ユーザーからの「話した内容の文字起こしもしっかり残しておいてほしい」という要望と噛み合ったため、文字起こし自体もその日の記録（DayInfo）に保存し、日の記録の下に折りたたみで表示する機能も一緒に実装

## エラー・つまずき

- Googleログインの設定作業の途中で、iOSアプリ内蔵WebViewでのOAuthブロックというプラットフォーム制約に気づいていなかった（ユーザーからの質問で発覚）
- 音声機能を実機で試したところ必ず失敗。`wrangler tail`でWorker側のログを見ると、CORSの事前確認（OPTIONS）は成功するのに本体のPOSTが一切届いていなかった。原因は、この機能だけが送る独自ヘッダー`x-voice-meta`をCORSの許可ヘッダー一覧に加え忘れていたこと。**Playwrightのテストは同一オリジンでAPIをモックしているため、この種のクロスオリジンCORS不具合は検出できない**というテスト手法の弱点も分かった
- CORSを直した後も失敗が続き、OpenAI側のエラー本文をログに出すよう改修して原因を特定。使っているモデルが音声を直接聞く方式（audio input）に対応していなかった
- ホーム画面の「マイ旅行」一覧（localStorageの索引）が、サーバー側でデータが削除された後も残り続け、「見つかりません」エラーになる不具合も同じ流れの中で発見・修正

## 解決方法

- iOSアプリ内では実質「Appleでサインイン」と「メールログイン（OTP）」の2つが使える前提に設計変更
- CORSの`access-control-allow-headers`に、音声機能が使う`x-voice-meta`を追加
- 音声認識をWhisper（音声認識専用API）による文字起こし→テキストでの構造化、という実績のある2段階構成に作り直した
- サーバー側で見つからない旅行は、開こうとしたタイミングでホーム画面の一覧（localStorageの索引）からも取り除くようにした

## 今日できるようになったこと

- 「ログインを作る」という一見シンプルな要望の裏にある、実行環境（ブラウザ／アプリ内蔵WebView）ごとの制約の違いに気づき、設計を作り直す
- 一度「要件が固まっていないため見送り」とした機能を、具体例が出て像が掴めたタイミングで`interview-me`から再開する、という企画の回り方
- 音声入力を「文字起こしをそのまま貼るだけ」ではなく「複数の予定・記録への分割・分類までAIにやらせる」設計にしつつ、「評価・費用・日付などAIが誤りやすい情報は今回のスコープに含めない」と線引きする判断
- `wrangler tail`でWorker側のリアルタイムログを見ながら、CORS不具合→AI呼び出し自体の不具合、と段階的に原因を切り分けて直す
- 実機で動かして初めて分かる制約（WebViewでのOAuthブロック、音声モデルの非対応）に、机上の設計だけでは気づけないことを実感し、実装後は必ず実機・実際のAPIで確認する重要性を再確認
- Claude Designのキャンバス機能で、実装済みの見た目を実際のCSS値のまま再現・レビューし、絵文字アイコンのような細かな崩れを見つけて直す

## 今日の動画で使えるポイント

1. 「Googleログインを作ろう」という何気ない一言から、「iOSアプリの中で本当に動くのか」というユーザーの鋭い質問で、AIが設計段階で見落としていた実行環境の制約（WebViewでのOAuthブロック）が発覚する場面
2. 音声で複数の予定をまとめて記録する機能を、机上では動くはずだったのに実機で試して初めて「モデルが音声を直接聞けない」というエラーに突き当たり、その場で設計を作り直す様子
3. `wrangler tail`でリアルタイムログを見ながら、「CORSで止まっている」→「直したらAI呼び出しで止まっている」→「エラー本文を出すよう改修して原因特定」という、段階的なデバッグの実演
4. Playwrightのテストが同一オリジンでAPIをモックしているために、本番でしか起きないcrossオリジンのCORS不具合を検出できなかった、というテスト手法自体の限界が見える場面
