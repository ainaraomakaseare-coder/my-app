## 実施作業

- 「野球観戦した試合を記録するベイ日記（横浜DeNAベイスターズ）を作りたい」というリクエストから開始
- 試合日・対戦相手・スコア・勝敗・球場に加え、同行者・チケット代・天気/気温・写真・自分なりのMVP/活躍選手・興奮したシーンを記録できるフォームを実装
- 年度別の観戦成績（試合数・勝敗・分・勝率）の自動集計と、年度切り替え一覧画面を実装
- 「選手分析」画面：MVP=2pt・その他の活躍=1ptで集計し、よく名前が挙がった選手をランキング表示（クリックで対象試合・メモを展開）
- 写真はアップロード時にcanvasで縮小・JPEG圧縮してから IndexedDB に保存（localStorageの容量制限を避けるため）
- データの書き出し・読み込み（JSONエクスポート/インポート、写真込み）を設定画面に実装
- 試合結果の自動取得について、NPB公式データを安定・無料で返すAPIの有無を調査したが見当たらず、`api-sports.io`の任意キーを使う試験的機能として実装し、失敗時は常に手入力にフォールバックする設計にした
- ロジックのユニットテスト（勝敗判定・年度集計・選手分析、20件）と、実ブラウザでの操作を確認するsmokeテスト（記録の追加・編集・削除・写真添付・選手分析・設定、27件）を作成し、全件通過を確認
- PR作成後、開発環境のリポジトリが古い状態のままだったことに気づき、`apps/day23-baydiary/`への移動、ルートの`README.md`・`index.html`・`docs/progress.md`の修正をやり直した（詳細は下記「エラー・つまずき」）

## エラー・つまずき

- 開発環境のローカルチェックアウトが、リポジトリが `apps/dayNN-アプリ名/` 構成へ整理される前の古いコミット（チンチロを単体アプリとして持っていた頃）のままになっていることに気づかず作業を開始してしまった。そのため新しいアプリをリポジトリ直下に `bay-diary.html` として配置し、その状態でPRを作成した
- PR作成後に`origin/main`を確認して初めて、実際にはDAY20まで進んだ「30日で30アプリ」構成（`apps/dayNN-アプリ名/`・`docs/logs/`・`docs/progress.md`のルール）になっていることが分かり、`main`とのマージコンフリクト（`README.md`の内容衝突、新規ファイルの配置場所の食い違い）が発生した
- NPBの試合結果を安定して無料で返すAPIが実在するか確認できず、npb.jpや主要な候補サイトへの直接アクセスも開発環境のネットワーク制限で検証できなかった。実際にAPIが使えるかどうかは、ユーザー自身がapi-sports.ioのキーを試すまで分からない

## 解決方法

- `git fetch`で`origin/main`の実際の状態を確認し、リポジトリ構成のズレに気づいた時点で作業を止めてユーザーに確認（DAY番号として企画に組み込むか、単発アプリとして切り離すか）
- `origin/main`をマージし、`bay-diary.html`と関連テストを`apps/day23-baydiary/`（`index.html`・`test/logic.test.js`・`test/ui.smoke.js`）へ移動。ルートの`README.md`はコンフリクトを解消して`main`側の構成を採用しつつ、DAY23の行とテストコマンドを追記。`index.html`のトップページにもカードを追加
- 移動後に`node test/logic.test.js`・`node test/ui.smoke.js`を再実行し、パスを直した上で全件通過することを確認
- API連携は「安定した無料APIの実在が確認できない」という事実をそのままREADMEと本ログに明記し、手入力へのフォールバックを必須の設計にすることでリスクを下げた

## 追記：API-BASEBALLの実キーで検証（マージ後）

ユーザーがapi-sports.io（API-BASEBALL）の無料キーを実際に取得し、ベイ日記から「試合結果をAPIから取得」を試したところ `Cannot read properties of undefined (reading 'id')` で失敗した。原因は、`/leagues`のレスポンス形式をAPI-FOOTBALLと同じ`{league:{id,name}}`という入れ子構造だと推測して実装していたが、API-BASEBALLは`{id,name}`という直接構造の可能性が高く、存在しない`.league`への`.id`アクセスで例外になっていたこと。ドキュメント確認は開発環境のネットワーク制限で今回もできなかったため、`l.league || l`という形で両方の形式を許容する防御的な実装に直し、`/teams`・`/games`のレスポンス解析も同様に未確認箇所をnullチェックで固めた。

修正後、ユーザーが再度試すと今度は「チーム情報が見つかりませんでした」に変化。ユーザーにapi-sports.ioダッシュボードの「Live Demo」で`/leagues?country=Japan`を実際に叩いてもらい、レスポンス実物を確認したところ、以下が判明した。

- `/leagues`のレスポンスは推測どおりフラットな`{id,name,seasons:[...]}`構造だった（NPBは`id:2`）
- **`seasons`配列は新しい順に並んでいない**（`[2020,2026,2025,2019,...,2008,2009]`という順）。実装は`seasons[seasons.length-1]`（配列の最後）を「最新シーズン」とみなしていたため、実際には一番古い`2009`年を使ってチーム検索をしてしまい、2009年時点の名称（DeNA買収前の「横浜ベイスターズ」時代）と一致せず見つからなかったと推測される

`seasons`の中から`current:true`の要素（今回は2026年）を優先して使い、無ければ`season`の最大値を使うよう修正した。実際のレスポンスを使ったシミュレーションで`season=2026`が選ばれることを確認した。

修正後、ユーザーが再度試すと**再び「チーム情報が見つかりませんでした」**。ユーザーにLive Demoで`GET /teams?league=2&season=2026`（searchなし）を直接試してもらったところ、以下が判明した。

```
"errors": { "plan": "Free plans do not have access to this season, try from 2022 to 2024." }
"response": []
```

これはコードの不具合ではなく、**api-sports.io（API-BASEBALL）の無料プランの制限**そのものだった。無料プランは2022〜2024年シーズンのデータにしかアクセスできず、2025年・2026年（今シーズン）のデータは一切取得できない。つまり「観に行った今シーズンの試合を自動取得する」というベイ日記の主目的には、この無料APIは使えないという結論になった。

対応として、チームIDの特定だけは許可されている2024年シーズンにフォールバックして取得し（チームIDは年をまたいでも同じため一度特定できれば以降は使い回せる）、実際の試合結果取得が対象シーズン制限に引っかかった場合は、汎用的な「見つかりませんでした」ではなく`errors`に入っているAPI側のメッセージをそのまま表示するようにした。設定画面とREADMEにも、2022〜2024年シーズンのみ対応という制約を正直に明記した。この機能は今シーズンの用途では実質使えないが、後から過去シーズン（2022〜2024年）の試合を記録する場合には引き続き使える……はずだった。

ところが、ユーザーが実際に2024年の試合（2024/05/06 vs ヤクルト）で試すと、今度は`/games`側で別のエラーが返ってきた。

```
Free plans do not have access to this date, try from 2026-09-15 to 2026-09-17.
```

つまり`/teams`は「2022〜2024年シーズン」という粒度の制限だったが、`/games`（実際の試合結果）は**実行日（今日）を挟んだごく数日間の日付しか許可しない**、さらに厳しい制限だった。これはコードの不具合ではなく、修正済みのエラーメッセージ表示（`apiPlanError`）がAPI側の実際の制約をそのまま正しく見せてくれたことで判明した。

この時点で、「後から過去の観戦記録をつける」というベイ日記の使い方には、無料プランの`/games`はほぼ全く対応していないと結論づけた。これ以上コード側で回避する方法はなく（プランの契約上の制約のため）、設定画面とREADMEの説明を「基本は手入力、APIキーは任意でほぼ効果がない」というトーンに修正するにとどめた。

有料プラン（PRO Plan 月$15〜、ULTRA Plan 月$25、MEGA Plan 月$35）であれば日付・シーズンの制限が緩和される可能性があるが、ユーザーは個人の観戦日記アプリに月額$15以上を払う価値はないと判断し、**有料プランへの加入は見送り**。api-sports.ioのアカウントは無料のまま維持し、ベイ日記は手入力を基本運用とすることで決着した。新規の課金・購入は発生していない。
