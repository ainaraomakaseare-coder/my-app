## 実施作業

- ユーザーからの「旅の思い出を写真とともに振り返るアプリ」というリクエストを、Claude Designでビジュアルのモックアップ（たびログ）として先に作成。対話の中で要望が広がった（費用・評価・地図リンク・予約サイト・メンバー招待・別行動タグ・音声での旅程復元・DB化）ため、`interview-me` の考え方で優先度を確認する質問をはさんだ
- 確定した内容：見た目の参考はPolarsteps、音声での旅程復元機能は今回は見送り、データベース化は無料枠に収める方針
- `apps/day07-tabilog/` を新規作成。フロント（index.html・style.css・app.js）とバックエンド（Cloudflare Worker + D1 + R2、`worker/`）を分離して実装
  - Trip（旅行）・Episode（記録）の2つのテーブルで、旅行の日程・参加者・記録ごとの時間・場所・写真・費用・楽しかった度（★）・種類（観光／食事／宿泊／移動／その他）・地図URL・公式サイトURL・予約サイト名・別行動タグを持たせた
  - ログイン機能は作らず、旅行ごとに発行するIDを含むURLを知っている人だけが読み書きできる「リンク共有」方式にした
  - 写真はブラウザ側で縮小・圧縮してからWorker経由でR2にアップロードする構成
- `docs/logs/TEMPLATE.md` を元にこのログを作成。ロードマップ上のDAY番号はユーザーと保留中のため、学びの内容が合うDAY7を仮に割り当てた（`docs/progress.md` の表は未更新）
- ユーザーのCloudflareアカウントでD1・R2を作成し、Workerを実際に公開（`https://tabilog-api.hiroya-apps.workers.dev`）。ユーザーのWindows PC上でwrangler CLIを操作してもらう形で進めた
- 公開後、ユーザーから見た目（るるぶ風の演出をやめてSlackのようなモダンな見た目に）と、データの持ち方（記録を「大項目（予定）」「小項目（一人ひとりの記録）」の2階層に分け、別行動は同じ大項目に小項目を複数ぶら下げて表現する）について大きな修正依頼があり、フロント・Worker・スキーマを作り直した
- 動画添付（1本50MBまで）・詳細欄・Google/Appleログイン（任意設定、記録した人への自動入力用）・App Store公開に向けたiOSアプリ化（Capacitor + GitHub Actions）・プライバシーポリシー・申請下書きを追加
- `.claude/skills/` に、mattpocock/skills・addyosmani/agent-skillsから7つのSkill（codebase-design・grill-with-docs・to-spec・to-tickets・wayfinder・documentation-and-adrs・idea-refine・planning-and-task-breakdown）をMITライセンスのまま導入（プロジェクトスコープのみ。グローバルには追加していない）
- `interview-me` の型（仮説→確信度→一問ずつ質問→確定）で「要件定義の強化・デザインの見直し」をヒアリング。「各記録に評価と費用をつけたい」という最初期の要望のうち費用だけ実装され評価が漏れていたことを発見し、単純な★1個ではなく、カテゴリ別（飯ログ／ほてログ／アクティビティーログ／移動ログ／その他ログ）に整理し、複数の旅行を横断して振り返れる「マイログ」画面として要件を確定させた
- 確定した要件を実装：
  - Worker：D1に`ratings`テーブルを追加（entry×ログインした人ごとに1件、UNIQUE制約でupsert。既存テーブルは変更しないため過去データは消えない）。`PUT/DELETE /entries/:id/rating`・`GET /mylog?email=`を追加。`GET /trips/:id`のレスポンスにentryごとの評価一覧を含めた。旅行・予定・記録の削除時に紐づく評価も一緒に消すようにした
  - フロント：ログインを「アプリ全体の入り口をブロックする」仕組みから「評価・マイログを使うときだけ求める」仕組みに設計変更（閲覧・記録の追加は今までどおりログイン不要のまま）。記録の編集画面に★1〜5の評価ウィジェット（自分の評価はワンタップで即保存、みんなの平均も表示）、ホーム画面に新しい「マイログ」画面（カテゴリタブ×評価順/新しい順の切り替え）を追加
  - `CONTEXT.md`に評価・マイログ・ログインの位置づけ（本人確認であってアクセス制御ではない）を追記
  - Playwrightで実際の画面をスクリーンショット確認（ログイン前後・評価入力・マイログ一覧）してからテストに反映

## エラー・つまずき

- テスト実行時、`playwright` はグローバルにインストールされていたが、このリポジトリのフォルダからは `require('playwright')` が解決できず `MODULE_NOT_FOUND` になった（ローカルの `node_modules` が無く、Node標準のモジュール解決では `/opt/node22/lib/node_modules` のようなグローバル置き場を辿らないため）
- この作業環境（クラウドのサンドボックス）は組織のネットワークポリシーで `api.cloudflare.com` への接続がブロックされており、Cloudflareへのデプロイ作業を代行できなかった。ユーザー自身のPCで `wrangler` コマンドを実行してもらう形に切り替えた
- ユーザーのPCがWindows PowerShellで、`npm install` がスクリプト実行ポリシーによりブロックされた（`UnauthorizedAccess`）。また、R2の利用開始時にCloudflare側で支払い方法の登録（サブスクリプション契約。無料枠内なら0円）が必須だった
- 見た目を確認する手段が、実際に動くアプリ（ローカルサーバーの起動に手間取っていた）ではなく、先に作ったClaude Designのモックアップしか無かったため、コード側だけ直してもユーザーには変化が伝わらなかった
- 評価機能を設計する中で、「マイログ」で複数の旅行を横断して評価を見るには、ログインしたアカウント（メールアドレス）で誰の評価かをサーバー側に紐づける必要が新たに出てきた。一方でこのAPI・アプリ全体はサーバー側でGoogle/Appleのトークンを検証しない簡易的な仕組みのため、「メールアドレスさえ分かれば誰でもその人のマイログを覗けてしまう」という新しいプライバシー上の弱点が生まれた。本格的なトークン検証（JWKS・署名確認）まで実装するかどうかを検討したが、家族向けの低リスクな前提・既存の設計方針との一貫性・当日中に検証しきれないUX（トークン失効時の挙動）を考慮し、今回は既存の簡易的な仕組みのまま実装し、この弱点をREADME/CONTEXT.mdに明記する判断にした

## 解決方法

- `NODE_PATH=/opt/node22/lib/node_modules` を付けて実行することで解決した。恒久的にはこのアプリ用に `npm install playwright` するのが望ましいが、今回は環境側の制約としてこの回避策で確認した
- デプロイはユーザーのPC側で実行してもらい、こちらは手順を都度案内する形にした。PowerShellの制限は `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` で解消
- 見た目の修正依頼が来た際、コードだけでなくClaude Designのモックアップ側も同じ内容に直し、確認手段を用意した

## 今日できるようになったこと

- 保存先を端末内（localStorage）からサーバー（データベース）に変える設計判断と実装（Cloudflare D1・R2）
- ログイン機能を作らずに「リンクを知っていれば読み書きできる」共有の仕組みを設計する
- Claude Designで先にビジュアルのモックアップを作ってから、対話で要望を広げ、優先度を確認してから実装に入るという進め方
- ユーザー自身のPCでwranglerコマンドを実行してもらいながら、CloudflareへWorker・D1・R2を実際に公開する
- 公開後に来た「見た目」「データ構造」の大きな修正依頼に対し、モックアップとコードの両方を作り直す
- ネットワークポリシーでこちらの作業環境から外部サービスに繋げない場合、ユーザーの端末での作業に切り替える判断
- 「ログイン＝アプリ全体への関所」という最初の設計を、要件が変わったタイミングで「ログイン＝特定の機能（評価）だけの関所」に作り変える（既存のログイン関連のテストも、その前提の変化に合わせて書き直す）
- 新しい機能を追加するときに生まれる、機能単体では見えにくいセキュリティ上のトレードオフ（メールアドレスだけを鍵にする設計の弱点）に気づき、実装するかどうかをその場で判断してドキュメントに残す
- 外部からSkillを導入する際、「グローバルに入れるべきか・プロジェクトだけにすべきか」をユーザーと確認し、企画のルール（Skillは数を必要最低限に）と実際の運用を照らし合わせる
- Playwrightでの自動テストに加えて、実際の画面をスクリーンショットで目視確認してからテストコードに反映する（UIの見た目が意図通りかをコードだけで判断しない）

## 今日の動画で使えるポイント

1. 「まず見た目のモックアップを見せる→そこに乗っかって要望がどんどん広がる」という、要件が対話の中で育っていく様子がそのまま撮れる
2. グローバルにインストール済みのはずのツール（playwright）が、フォルダの位置によっては見つからないという、初心者がつまずきやすい「Node.jsのモジュール解決」の実例
3. 「音声で旅程を復元する」「AIで旅程を整理する」など魅力的な追加要望が次々出てきても、その場で全部やらずに「今回はここまで」と線を引く判断も動画の見せどころになる
4. Cloudflareへの実際のデプロイを、Windows PowerShellでのつまずき（実行ポリシー、日本語表示）を含めてそのまま追体験できる
5. AIの作業環境自体がネットワークポリシーでブロックされ、「代わりにやります」が通用しない場面があるという、AIの限界が見える瞬間
6. ユーザーが寝る前に「大きな変更でも判断して進めていい、お金がかかることだけ相談して」と一言残すだけで、要件のヒアリング→設計判断→実装→テスト→ビジュアル確認→ドキュメント更新までを一晩で終えられる、という自律的な開発の実例
7. 「評価機能をどう作るか」を決める過程で、機能追加のはずが「今のログインの設計（アプリ全体をブロックする関所）を見直す」という、当初想定していなかった既存設計への手戻りが必要になった場面（要件は後から育つと、前の設計判断まで揺さぶられることがある）
