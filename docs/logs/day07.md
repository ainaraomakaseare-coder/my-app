# DAY 7：サッカー出欠管理

**新しい挑戦**：初めてデータベースを使う。アプリを閉じても入力した内容が残る状態を作る。

**実作業は約30分。しかし終わるまでに10時間以上かかった。**差は、セッションの利用上限に
**2回**達し、そのたびにリセットを待った時間である。

### 自動計測は当てにならなかった

`node .claude/hooks/timelog.js report` の出力：実時間 **3h19m**（08:09〜11:29）、AI稼働 **0s**、やり取り 0 回。

**この数字は2つとも間違っている。**

1. **AI稼働 0s** は「動かなかった」ではなく「測れなかった」。今回 Claude Code をブラウザ側の
   リモート環境で動かしており、作業ディレクトリがアプリのリポジトリ側ではないため、
   `.claude/settings.json` のフック（`UserPromptSubmit` / `Stop`）が一度も発火しなかった。
   記録に残ったのは手動で打った `start` と `stop` の2点だけ。
2. **実時間 3h19m** も実際の経過（10時間以上）と合わない。リモート環境のコンテナは
   待ち時間のあいだ動いておらず、コンテナ内の時計が実時間を追いかけていなかったとみられる。
   **つまりこの環境では、フックによる自動計測は経過時間そのものを取りこぼす。**

したがって記入するのは本人申告の「人間作業 約30m」のみとし、AI実稼働は推測しない。

### 次回への申し送り

- リモート環境で作業する日は、**アプリのリポジトリを作業ディレクトリにしてセッションを開始**しないとフックが効かない。
- それでも待ち時間中はコンテナの時計が進まないため、**経過時間は人間が時計で控える**必要がある。
- 自動計測を信じ切らず、開始時刻と終了時刻だけは自分でメモしておくのが確実。

## エラー・つまずき

1. **GitHub のリポジトリを AI 側から作れなかった。** `create_repository` が
   `403 Resource not accessible by integration`。連携中の GitHub App にリポジトリ作成権限が無い。
   時間を空けて再試行しても同じ。**人間が画面から作るしかなかった**。
   （最終的に本人が作成 → AI 側で remote を繋いで push し、解決）
2. **`timelog.js mark` を手で叩くと固まる。** フックは Claude Code が stdin に JSON を流す前提で
   `readStdin()` を呼んでおり、手動実行だと入力待ちのまま止まる（2分でタイムアウト）。
3. **コンテナの時計が UTC だった。** そのまま記録すると JST 8/27 朝が「8/26」として保存され日付が1日ずれる。
4. **セッションの利用上限に2回達して中断。** 実装の途中で止まり、リセットを待って再開。
   **実作業30分に対し、完了まで10時間以上。**今日の所要時間を決めたのは、作業量ではなく待ち時間だった。
   `progress.md` に「まだ配置していないつまずき」として挙がっていた項目が、今日実際に起きた。
5. **`.gitignore` の書き漏れ。** 接続情報が入る `config.local.js` を除外し忘れており、
   **コミット直前の確認で、上がる寸前だった**。`.env` だけ守れば安心、ではなかった。
6. **開発環境から Supabase に通信できなかった。** ネットワークポリシーで `supabase.com` が遮断されており、
   公式の料金ページも見られず、実接続テストもできなかった。
7. **Playwright のブラウザ版数が合わなかった。** 環境には 1194 が入っているのに、
   インストールした Playwright は 1234 を探しに行って起動失敗。
8. **時間の自動計測が両方とも狂っていた。** 上記「時間」の項を参照。
9. **`pkill -f` が自分自身を巻き込んだ。** サーバーを止めるつもりで打ったパターンが、
   その文字列を含む実行中のシェル自体にマッチして、作業ごと落ちた。ポート番号から
   プロセスを特定する方法に変更。
10. **テストが1件、実装ではなくテスト側の理由で落ちた。** 「読み込み中…」の表示が
   実データと同じ `.chip` だったため、読み込み完了前に数えていた。
   紛らわしいのでアプリ側にも `loading` を付けて区別できるようにした。

## 解決方法

1. → 本人に GitHub の画面で作ってもらい、`git remote add` して push。
   作れないのは「作成」だけで、既にあるリポジトリへの push は問題なくできた。
2. → `node .claude/hooks/timelog.js mark start < /dev/null` と stdin を塞いで実行。
3. → `TZ=Asia/Tokyo` を付けて実行。
4. → リセット後に再開。作業内容は失われなかった。
5. → `.gitignore` に `config.local.js` を追加。さらに**コミット前に、実際に上がる差分を
   `supabase.co` / `eyJ...` / `service_role` などで全文検索する確認**を入れた。
   検出されたのは README の説明用ダミーのみであることを確かめてからコミット。
6. → 料金は第三者のまとめ記事で確認し、公式で再確認するようユーザーに依頼。
   実接続の代わりに、**手元に PostgreSQL 16 を立て、Supabase の役割（anon）を再現して検証**。
   さらに Supabase の REST API を模したサーバーを書き、実ブラウザで通しテストまで実施。
7. → `chromium.launch({ executablePath })` で環境内の Chromium を直接指定。
8. → 推測で埋めず「正確な計測不可」と記入。次回への申し送りを残した。
9. → `ss -lptn 'sport = :8000'` でポートから PID を引いて kill。
10. → 「読み込み中…」に `loading` クラスを付け、テストは `:not(.loading)` を待つように修正。

## 設計の判断（動画の芯）

**ログイン方式が3回変わった。**

1. 当初「ログイン不要・端末が名前を覚える」を提案 → ユーザーが「毎週やるのにログイン要らない？」
2. **私の説明に誤りがあり訂正。** Supabase はセッションを端末に保持して自動更新するため、
   一度ログインすれば数ヶ月維持される。「毎週ログインが面倒」という私の論拠は間違いだった。
3. ユーザーが「メールログインやろうよ」→ 調べると Supabase 標準のメールは**1時間2通**。
   外部業者＋独自ドメインで**実費が発生**すると判明。代案として Google ログインを提案。
4. ユーザーが運用を説明（「こちらからメールはしない。LINEで出欠登録してと流す。今はスプレッドシート」）
   → **LINEの内蔵ブラウザは Google ログインを弾く**（`403: disallowed_useragent`）と判明。Google 案も脱落。
5. 最終案：**個人リンク方式**。マネージャーが各人固有のURLを LINE で配る。
   マジックリンクの、配達手段をメールから LINE に置き換えた形。ログイン画面ゼロ、費用ゼロ。

**「どうやって使うか」を聞かないと技術選定を間違える**という実例になった。

## 今日の動画で使えるポイント

1. **実作業30分。終わったのは10時間後。** 止まっていた理由は、コードでもエラーでもなく
   **セッションの利用上限のリセット待ち**（2回）。しかも**自動で時間を測る仕掛けを入れていたのに、
   出てきた数字は「AI稼働 0s／実時間 3h19m」で、どちらも実態と違った**。
   フックが発火せず、待ち時間のあいだコンテナの時計も進んでいなかった。
   「計測してるから大丈夫」が一番危ない、という話にできる。企画のルールどおり
   推測では埋めず「正確な計測不可」と書いた。

2. **「キーをGitHubに上げるな」の一段先。** Supabase のキーは**ブラウザに出ていい**。
   初心者はここで必ず「え、公開していいの？」となる。守っているのは鍵の秘密ではなく
   データベース側の RLS。しかもそれを**テストで証明した**——わざと anon にテーブルの
   読み書き権限を与えた上で、それでも1行も見えないことを確認。RLS を切ると即座にテストが赤くなる。

3. **「メールログインやろうよ」が3回ひっくり返った。** メール→1時間2通の壁→ドメイン代が要る→
   Googleログイン→**LINEの内蔵ブラウザが弾く**→個人リンク方式。決め手は技術ではなく、
   ユーザーの一言「連絡はLINEで流す。今はスプレッドシート」。要件ヒアリングが効いた瞬間。
   途中でAI側の説明の誤りも判明して訂正が入っている。
