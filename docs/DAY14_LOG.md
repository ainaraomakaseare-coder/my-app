## 先に調べたこと — どのSNSで何が取れるか

| SNS | 取れるもの | 状況 |
|---|---|---|
| **YouTube** | 登録者数・総再生数／動画ごとの再生・高評価・コメント | ✅ **すでに権限あり**（`youtube.readonly`）。追加作業ゼロ |
| **Instagram** | いいね数・コメント数・フォロワー数 | ✅ **本番で確認済み**（下記）。追加の権限も審査も不要だった |

### X を外した判断

**API では自分のポストの数字すら読めません。** 無料枠は投稿専用です。
「コストが追加でかかる場合だけNG」に真正面から当たるため、対象から外しました。

ただし X の管理画面（analytics.x.com）では自分の数字を無料で見られるので、
**手入力欄を足せば同じ画面に並べられます**。今回は作らず、必要になったら足せる
形にしてあります。転職チャンネルは A8 が X を対象外にしているので、
アフィリの判断材料としての優先度も低いと判断しました。

### TikTok は投稿と動画が結びつかない

調べて分かった制約です。アプリが TikTok に残している `external_id` は
**`publish_id`（下書きの整理番号）**で、動画IDではありません。TikTok は下書きに
届いた時点で完了扱いになり、公開は本人が後から手でやるため、**アプリのどの投稿が
どの動画になったのかを知る手がかりがありません。**

投稿時刻の近さや本文の一致で推測して結びつけることもできますが、
**間違った組み合わせで「この台本が伸びた」と読んでしまう**と、数字を見る意味が
壊れます。結びつけず、TikTok 側の一覧として別に置く設計にしました。

## 実施した主な作業

### 1. 数字をためる場所（`schema_v8_insights.sql`）

どのSNSのAPIも「いまのフォロワー数」しか返さず、履歴はくれません。
**毎日こちらで書き留めないと、あとから伸びは分かりません。
始めた日より前のことは、永久に分かりません。**

- `account_metrics` … アカウントの数字。**同じ日は1行**（後の値で上書き）
- `target_metrics` … 投稿ごとの数字。`post_targets` にぶら下げる
- `tiktok_videos` … 結びつかない TikTok の一覧
- `jst_today()` … 日本時間の今日

**取れなかった日も `ok=false` で残します。** 「0だった」と「取りに行ったが断られた」は
別物で、後者は権限を直せば取れます。区別できないと原因を追えません。

### 2. 言えることだけ言う（`lib/advice.js`）

**このアプリでいちばん神経を使った部分です。**

20本・20日ぶんのデータで「21時より20時が伸びる」のような話をすると、
偶然の差を法則として読んでしまいます。もっともらしい分析文を書くのは簡単ですが、
**それは投稿文に課している「嘘を書かない」を、こちら側が破ることになります。**

| 状況 | 何と言うか |
|---|---|
| 投稿が3本 | 「5本たまると比べられます」 |
| 全部似た数字 | 「**いまの差は偶然の範囲と区別がつかない**ので、この切り口が効いたとは言えません」 |
| 差がある（6本） | 順位を出す。ただし「次の数本で入れ替わる可能性があります」 |
| 10本あって差がある | 断りなしで順位を出す |
| ペース差が1日0.5人未満 | 「速くなったとも遅くなったとも言えません」 |

- 比べるのは**平均でなく中央値**。1本跳ねると残り全部が「平均以下」に見えるため
- 並びは **直せること → 確かなこと → まだ言えないこと**
- **取れていないアカウントについては、伸びの話を一切しない**
  （「伸びていない」と「測れていない」が混ざるため）

### 3. SNSから数字を読む（`lib/insights.js`）— Sonnet

**報告を信用せず、実際にありそうな壊れ方を6通り投げ直して確認しました。**

```
Instagram 200だがフィールドが無い  → ok:true, followers:null, error に Meta の原文
Instagram フィールド単位のエラー    → ok:true, error にコードと原文
Instagram 400 で落ちる              → ok:false
Instagram JSONですらない返事        → ok:false
Instagram 通信が落ちる              → ok:false
YouTube 登録者数が非公開            → ok:true, followers:null（エラーではない）
```

**1つのSNSが失敗しても他を巻き込まないこと**が、ここでいちばん大事です。

### 4. 毎晩の取り込み（`api/insights.js` / `lib/metrics-store.js`）

- `POST /api/insights` … cron の鍵で守る（worker と同じ守り方）
- `GET /api/insights?group=…` … 画面が読む
- `GET /api/insights?probe=…` … **接続テスト。SNSが返した中身をそのまま見せる**

**1アカウント処理するたびに書き込みます。** 最後にまとめて書くと、制限時間に
切られたとき全部消えます。取り込みは1日1回しかないので、消えるとその日は
取り返せません。

### 1. TikTok を繋ぐと AI 側が繋ぎ直された

連携し直しで行が増えないよう「同じSNSで同じ**表示名**なら同じ連携先」とみなして
上書きしていました。ところが TikTok の表示名は権限しだいで取れず、取れないと
`TikTok` という固定の文字に落ちます。

```
1つ目（AI初心者）を繋ぐ → 表示名が取れず account_name = 'TikTok'
2つ目（転職）を繋ぐ     → 同じく 'TikTok' → 同じ連携先と判断 → 1つ目を上書き
```

引換券も所属も上書きされるので、**AI初心者側の TikTok が転職のアカウントに
差し替わっていた**ことになります。一覧では TikTok が1行のままなので気づけません。

→ **SNS が発行する変わらないID**（TikTok の `open_id`、X の user id、
YouTube のチャンネルID、Instagram の `user_id`）で見分けるようにしました（v7）。
さらに、すでに別チャンネルにぶら下がっている相手なら**黙って奪わずに断る**ように。

### 2・3. 「頼んでも守られない」ものは、コードで保証する

同じ構図のつまずきが2つ続きました。

| つまずき | プロンプトでの指示 | 実際 |
|---|---|---|
| 動画の右が見切れる | 「問いと答えで15字以内」 | 1本目は**6行すべて超過** |
| 下書きで止まる | 「出典の断りを必ず入れる」 | 書き落として予約されず |

**どちらも頼み方を強めても保証になりません。** 直し方を揃えました。

- 動画 … はみ出す行は**縮めて収める**（6行そろえて、0.55倍を下限に）
- 断り … 無ければ**こちらで一文足す**（黙っては足さず、画面に出す）

断りを足してよい理由は、その一文が「運用者に実体験は無く、ネットの声を集めている」
という**誰が書いても変わらない事実**だからです。落ちたまま出るほうが、
体験談に見えて問題になります。

なお動画のはみ出しは、**画素を数えて調べたら文字ではなくタイトルの下の赤い線**でした
（文字の右端より3px長く引く作りのため）。

### 6. 名前の途中で文が切れた

断りの用件と直し方を1本の文字列に `｜` で詰めて渡していたため、
**`ひろや｜AI初心者30日30アプリ`** のように `｜` を名前に含むチャンネルで、
名前の真ん中で改行されて意味不明になりました。別々の値で渡すよう直しました。

### 9. cron の鍵をプレースホルダのまま登録した

README が「`＜CRON_SECRET＞` を実際の値に置き換えてください」という書き方だったため、
置き換えないまま登録してしまった。**毎晩 401 で静かに失敗し続ける**形で、
数日後に「溜まっていない」と気づくことになるところだった。

→ **手で鍵を貼らせる手順を書いていたのが原因。** すでに動いている worker の設定から、
宛先だけ差し替えて作る形に README を書き換えた。

```sql
select cron.schedule('toukoutaku-neo-insights', '30 14 * * *',
  regexp_replace(replace(command, '/api/worker', '/api/insights'),
    'timeout_milliseconds\s*:=\s*\d+', 'timeout_milliseconds := 50000'))
from cron.job where jobname = 'toukoutaku-neo-worker';
```

確認も、鍵を画面に出さずにできる形にした（`command like '%<%'` が false かを見る）。

### 10. 確認用SQLが、失敗を隠す形だった

「まだ届いていない」のか「弾かれた」のかが区別できない。
worker を除外する形（`content not like '%checkedAt%'`）に直した。

## 分析として足りていないもの

**いちばん大きな問題は、データ量ではなく「何を試したか」が記録されていないこと。**

いま1本の投稿に残っているのは、これだけです。

```
title / rows / 各SNSの本文 / hashtags / tone（calm・plain・alert）/ 予約時刻
```

20本たまれば「どれが伸びたか」の**順位は出せます**。ただし
「**なぜ伸びたか**」は出せません。全部ネタが違うので、差が出ても
「そのネタがたまたま良かった」以上のことが言えないためです。

改善につなげるには、**1つだけ変えて比べる**必要があります。

```
× 20本ぜんぶ違うネタ・違う書き方  → 順位は出るが、次に活かせない
○ 10本は「問いかけ型」、10本は「断定型」 → どちらが効いたか言える
```

`tone` は投稿ごとに記録されているので軸として使えますが、
20本を3つに割ると1グループ7本弱で、比較には足りません。**2つに絞る**ほうが早い。

→ **投稿に「ねらい」を1つ記録する欄**を足せば、「A型の中央値 vs B型の中央値」が
出せます。**仕込んだ後では手遅れ**（印は投稿と一緒に保存するため）。
