# 時差のある旅行は、表示は現地時間・並びは世界共通の時刻

海外旅行で「20時出発なのに10時着」のように、時差をまたぐと前後関係がおかしくなる、という声があった（2026-09-25）。時刻を現地時間のまま並べていたため、日本20:00発→ハワイ同日10:00着（日付変更線をまたぐ）では、着が発より前に並んでいた。

**決めたこと**：
- **時刻の入力と表示は現地時間のまま**（チケットや現地の時計の時刻をそのまま入れられる。換算の手間と間違いを避ける）
- 予定ごとのタイムゾーンを自動で決める。優先順は、その予定の場所（記録の地図の座標）→ 地図が無ければ直前の予定（ただしその日の最初の予定は直前が別の日なので引き継がず、その日の場所＝天気の場所を使う）→ 端末のタイムゾーン。地図の無い予定を毎回「その日の場所」に戻すと、移動日（例：成田を地図付きで出発→現地に地図付きで到着→地図の無い予定→また地図付きの予定）で地図の無い予定だけ出発地に巻き戻り、「ここから現地時間」の区切りが行ったり来たりしてしまうため、直前の予定を引き継ぐ形にした（2026-09-26）。**移動の予定の時刻は出発の時刻なので、出発地（直前の予定）のタイムゾーンで読む**。「直前の予定」は時差を考えた順でないと決まらないので、仮に決めて並べてからもう一度決める（`Core.assignBlockZones`）
- タイムゾーン名はWorker（`/timezone`、天気と同じOpen-Meteo、無料・30日キャッシュ）で求め、時差（サマータイム込み）はアプリ側でIntlが計算する（`Core.tzOffsetMinutes`）。端末にも保存し、2回目からは通信しない。旅行を開いたあと裏で調べ、分かったら描き直す
- **同じ日の中の並びは、世界共通の時刻**（現地の分 − 時差）で比べる。日タブは現地の日付のまま
- 時差の違う場所に移ったところに「🕒 ここから現地時間（ハワイ・アリューシャン標準時・日本との時差 −19時間）」の区切りを出す
- 移動の所要時間は時差を考えて計算し、到着が現地の翌日なら「翌」を付ける（例：20:00発 → 翌01:00着（14時間・時差−9時間））
- 地図でふりかえるの時間軸も世界共通の時刻にし、時計は今いる場所の現地時間で出す。時差が変わったら「時差 −19時間（ここから現地時間）」のバナーを出す

**見送ったこと**：日付変更線をまたいで現地の日付が逆になるまれなケース（日本1/2 01:00発→ハワイ1/1 13:00着など）は、日タブが現地の日付なので、着が前の日のタブに出る。現地のカレンダーどおりなので、そのままにした。

**追記（2026-09-26）日付変更線を東へ越える移動日**：成田6/26 20:00発 → ロサンゼルス6/26 18:00着のように、着の現地時刻が発より早い日は、「仮に現地時間の順で直前の予定を決める」方法だと着が発の直前に来て、発もロサンゼルス時間で読まれ、着→発のまま固まっていた。移動の予定がある日は、出発地のタイムゾーンの候補（前の日から続くタイムゾーン、その日に出てくるタイムゾーン）を全部試し、①出発地＝時差を考えた順で直前の予定のタイムゾーン、が最も多く成り立つもの（直前が移動の予定なら、その地図が出発地か到着地か分からないので成り立つとみなす）、②その中で予定を入れた（並べ替えた）順（createdAt）と最も食い違わないもの、③前の日から続くタイムゾーン、の順で選ぶ（`Core.assignBlockZones`）。1日目の「前の日から続くタイムゾーン」は端末のタイムゾーン。旅行としての順（発→着）を、時計の上で過去に見える時刻より優先する。


**改訂（2026-09-27）時差は「移動」のところでしか変わらない**：予定1つ1つの地図からタイムゾーンを決める方法では、地図が1つ別の国と判定されただけでそこだけ時差が入って戻り、「香港に到着」のような移動の予定を出発時刻として前の場所で読むため到着ではなく出発のところで時差が入り、地図の無い予定に使う「その日の場所」がずれているとニューヨークで「日本との時差ゼロ」が出ていた（ブラジル・アルゼンチン旅でオーナーが確認）。オーナーの方針で、旅を「かたまり」に分け、かたまりの中は同じタイムゾーンにした（`Core.assignBlockZones` → `segmentZones`）。
- 切れ目：①飛行機の移動の予定のあと（移動の予定自身は出発地）②移動手段が飛行機の予定の前 ③移動の予定の地図のタイムゾーンが今のかたまりと違うとき（移動先の地図とみなす）④地図のタイムゾーンが変わり、次の地図でも変わったまま
- 1つだけ前後と違う地図（前後は同じで間に飛行機が無い）は判定違いとして外す（`withoutZoneOutliers`、日付と現地時刻の素直な順で先に見る）
- かたまりのタイムゾーンは中の地図のもの。地図が無ければ、飛行機で出発するだけのかたまりは前のかたまり（旅の最初は端末）、それ以外はその日の場所→前のかたまり→端末
- 飛行機の予定の地図は、今いる場所と同じタイムゾーンなら出発地、違えば到着地とみなす
- 並び順（日付変更線をまたぐ日）は、これまでの決め方（`orderZonesByCandidates`）で一度付けたタイムゾーンで並べたものを使う
- 「その日の場所」で翌日の地図の無い予定のタイムゾーンを決めるのはやめた（移動の予定が無ければ同じかたまり）
- 追記（同日）：日付変更線をまたぐ日の並び（東京20:00発→ロサンゼルス18:50着）は、以前は前後の話がどちらでも合うときに「予定を入れた順」で決めていたため、到着を先に入れた・逆順に入れた旅で着→発に並んでいた。飛行機の予定の時刻は「いまいる場所」（前の日から続くタイムゾーン、旅の最初の日は端末）で読み、その日に飛行機の予定が2つ以上あって地図が「いまいる場所」と違うものは到着の予定としてその土地の時間で読む（そういう予定が複数あるときだけ見出しの「到着」で見分ける）。これを「予定を入れた順」より優先する。入れた順3通り×フライトの地図3通り×到着の入れ方2通り×その日の場所2通りの36通りをテストで固定した（変更前は24通りで着→発）。予定の入力画面に「日付・時間は現地時間で」の一文を足した。

**改訂（2026-09-29）「直前の予定のタイムゾーン」を引き継ぐ移動の予定に、自分の地図での安全策を追加**：`orderZonesByCandidates`の`walkDay`は、移動の予定（`isTransport`）で自分の地図から出発地・到着地を判定できない（`isGroundMove`が成り立たない）ときは「直前の予定のタイムゾーン」を引き継ぐ。ふだんは`segmentZones`・組み合わせの試行（`combos`）が先に正しい順へ直すが、その日の移動の予定が3件を超える・未対応の言い回しで飛行機と判定できない、などで組み合わせの試行が働かない場合に備え、`walkDay`自身にも安全策を追加した：直前のタイムゾーンをそのまま使うと、その予定の絶対時刻（世界共通の時刻）が直前の予定より前に来てしまう（＝到着が出発より前に見える）ときは、自分の地図（＝到着地）のタイムゾーンを使う。自分の地図が無ければ、これまでどおり直前を引き継ぐ。「大谷観戦旅」の羽田18:30→LAX18:50着→羽田20:00発フライト→ユニオン20:20着の並びをテストで固定した（`test/data.test.js`）。

**追記（2026-09-29）前後から遠く離れたピン（違う場所のピンが残っている）**：ヒューストン滞在中の1日だけ、記録の地図にロサンゼルスの自宅のピンが残っていた（前後の記録はヒューストンで、前後どうしは近いのに、その1件だけ800km以上離れていた）。`Core.isFarMapOutlier(prev, cur, next)`／`Core.findFarMapOutlierBlockIds(blocks)`を追加し、前後の記録とは800km以上・前後どうしは300km未満のときだけ「ピンを間違えている」とみなす（本物の長距離移動は前後どうしも遠いので当たらない）。地図でふりかえる（`buildReplayTimeline`）では、そのピンは地図の地点にせず（`located=false`、`outlier: true`）、吹き出し（キャプション）だけ出す。旅行詳細画面では、その記録の「地図」リンクの下に「この地図は前後の予定から遠く離れています（地図が違うかもしれません）」と出し、押して直せるようにした（`renderEntryEl`、`.map-far-outlier`）。

**改訂（2026-09-29）到着地の地図がある移動のあとは、地図の無い予定も到着地を引き継ぐ**：実データ（「大谷観戦旅」1日目、手で並べ直した日）で、LAXの到着時刻を直しただけで「ロサンゼルスへのフライト」が現地時間（ロサンゼルス）側に移ってしまう不具合が見つかった。原因は2つ重なっていた。
① `orderZonesByCandidates`の`walkDay`が、移動の予定のあとに引き継ぐ「いまいる場所」（`prevZone`）を自分の地図（＝出発地）のままにしていた。到着地の地図（`byArrive`）があるのに出発地のままだと、そのあとの地図の無い予定（ファンゾーンなど）が出発地（日本）の時差を引きずり、`segmentZones`が並べ替えに使う`_offset`（世界共通の時刻）が実際の順と食い違って、移動の予定自身の時差まで巻き戻ることがあった。移動のあとの「いまいる場所」は、到着地の地図（`byArrive[b.id]`）があればそれを優先するようにした。
② `orderZonesByCandidates`内の「出発地の地図＝到着地の地図なら行き先の地図とみなし、いまいる場所で読む」という判定（`planeWant`）が、飛行機以外の地上の移動（車のユニオンステーションなど）にもかかっていた。地上の移動は出発地・到着地とも別々の実在する地図で、たまたま同じ時差というだけのことがあるので、この判定は飛行機（`isPlaneMove`）のときだけに絞った。
実データ（`trip_4e6c13ab396540b3b207108efb4c6f54`、6/26。羽田の地震→ロサンゼルスへのフライト→LAX到着→ユニオンステーション→…、`manualOrder`・到着地の地図を含む）で、LAXの到着時刻をいろいろ変えても常にフライトは日本時間・区切りはフライトとLAXの間、と固定するテストを追加した（`test/data.test.js`）。

**追記（2026-09-29）前後から遠く離れたピンは、時差の手がかりからも外す**：上の「前後から遠く離れたピン」の対応（`isFarMapOutlier`／`findFarMapOutlierBlockIds`）は、地図でふりかえる・警告表示にだけ使っていて、時差の判定（`assignBlockZones`）はそのままだった。実データ（同じヒューストン滞在日、`trip_4e6c13ab396540b3b207108efb4c6f54`、6/28）で、22:30のマリオット（前後はヒューストンなのに、地図だけロサンゼルスの自宅のピンが残っていた）の直前に「🕒 ここから現地時間…時差 −2時間」の区切りが出てしまっていた。その記録自身の地図（`byBlock`）でタイムゾーンを決めているため、間違ったピンがそのままロサンゼルス時間として読まれていた。`assignBlockZones`の先頭で`findFarMapOutlierBlockIds`を呼び、外れ値と判定された予定は`byBlock`から取り除いてから並べ替える（地図が無い予定と同じ扱いになり、直前の予定のタイムゾーンを引き継ぐ）ようにした。地図そのもの（吹き出し・「この地図は前後の予定から遠く離れています」の警告表示）は変えていない。ヒューストン到着→マリオット→Truth BBQ→（地図の無い夕方の予定2件）→22:30マリオット（間違ったピン）→翌朝First Watch、の並びで22:30の予定もヒューストンの時差のまま・区切りが増えないことをテストで固定した（`test/data.test.js`）。

**改訂（2026-09-29）時差は地図の場所だけで決める。旧来の推測ロジックは全部撤去し、手で直せるようにした**：ここまで積み重ねてきた「かたまり分け」（`segmentZones`）・「日付変更線をまたぐ日の候補探索」（`orderZonesByCandidates`のcombo探索）・「地上の移動／飛行機の判定」（`isGroundMove`）・「1つだけ前後と違う地図を判定違いとして無視する」（`withoutZoneOutliers`）・「その日の場所（day_infos／byDate）」・見出しの文言（「到着」「〜へ」「フライト」など）からの出発／到着の推測は、実データが増えるたびに新しい例外にぶつかり、そのたびに条件を積み増していた（このADRの改訂履歴がそのまま証拠）。オーナーから明確な方針が出た（2026-09-29）：

> ヒューストンとか書いてあるからって勝手に時差移動させないでほしい。マップが正。マップ入れてなかったら前の予定と一緒で大丈夫。勝手に推測するのはやめてほしい（ラスベガスのニューヨークニューヨークというホテルをニューヨークと判断されたらややこしい）。時差のところは人がいじれなくなっているので慎重に。間違っていたら削除くらいはできてもいい。時間を変えられるのも、やりすぎない範囲で。

これを受けて、`Core.assignBlockZones`を次のシンプルな規則だけに作り直した（`orderZonesByCandidates`・`walkDay`・`segmentZones`・`withoutZoneOutliers`・`startZoneFor`・`isGroundMove`は削除。`isPlaneMove`は記録フォームの「移動の情報」欄の出し分けにのみ残した）：

- **予定の時差＝その予定「自身」の地図（記録の地図）**。移動の予定（`category === 'transport'`）は地図＝出発地として読む（時刻は出発の時刻のため）。移動の情報の到着地の地図（`travel.arriveMapUrl`）があれば、そのタイムゾーンを**次の予定から**使う（`byArrive`）
- **地図が無い予定は、直前の予定（表示順。手で並べた日は`manualOrder`の順）のタイムゾーンをそのまま引き継ぐ**。旅の最初の方に地図の無い予定が続くときは、旅の中で最初に地図が出てくる予定のタイムゾーン（それも無ければ端末のタイムゾーン）
- 見出しの文言・その日の場所・予定を入れた順からは一切推測しない。1つだけ前後と違う地図も、それが今その予定の地図である以上そのまま使う（判定違いの無視はしない）
- 前後から遠く離れたピン（`isFarMapOutlier`／`findFarMapOutlierBlockIds`、ピンの座標どうしの距離で決める＝地図に基づく判定なのでこれは残した）は、引き続き地図が無いのと同じに扱う
- 並び順は、これまでどおり世界共通の時刻（`sortBlocks`）。地図の無い予定の直前が何かは表示順で決まり、表示順は時差が分かって初めて決まるので、`walkZones`を数回（最大3回）繰り返して落ち着かせる（`assignBlockZones`）

**手で直せるようにした**：自動の判定が間違っているときのために、「🕒 ここから現地時間」の区切りをタップすると小さなシートが開き、次を選べる（`renderZoneDivider`・`openTzOverrideSheet`、`app.js`）。
- 「この時差を取り消す（前の予定と同じ時間にする）」→ その予定に`tzOverride: 'inherit'`を保存する（直前の予定の時差になり、区切りが消える）
- 「タイムゾーンを選ぶ」→ この旅行に出てくる地図のタイムゾーン（重複なし）＋日本＋「その他…」（主要な約20のタイムゾーンから選べる）から選び、そのIANA名を`tzOverride`に保存する
- 「自動に戻す」（直した値があるときだけ）→ `tzOverride`を空にする

直した予定・区切りには「時差を手で直しています」の注記を出す。保存先は`blocks.tz_override`（migrations/0027、`ALTER TABLE blocks ADD COLUMN tz_override TEXT`）。値はNULL／空文字＝自動、`'inherit'`、またはIANA名。`PATCH /blocks/:id`で受け取り（`TZ_OVERRIDE_RE`で検証）、`GET`系は`tzOverride`として返す。列がまだ無い環境では書き込みだけ失敗を握りつぶす（`manual_order`と同じtry/catchのパターン）ので、マイグレーション未適用の間は手直しが保存されないだけで他の操作は壊れない。

テストは、World Cup 6/26（羽田の地震→ロサンゼルス国際空港→ロサンゼルスへのフライト→ユニオンステーション）とヒューストンの間違ったピンの回帰ケースを地図だけの形に単純化して残し、ラスベガスの「ニューヨークニューヨーク」ホテル（地図はラスベガス）が見出しに関わらずロサンゼルス時間のままになること、見出しの文言だけでは時差が変わらないこと、`tzOverride`の3パターン（`'inherit'`・IANA名・連鎖）を追加した（`test/data.test.js`）。日付変更線をまたぐ日の並びを「予定を入れた順」「見出しの種類」「その日の場所」の組み合わせで固定していたテスト（36通り・24通りなど）は、前提となるcombo探索ごと削除した。
