# 旅行の公開範囲（全体・フォロワー・親しい友人・一緒に行った人）

SNSらしく、旅行ごとに見られる人を選べるようにしたい、という要望があった（2026-09-26）。範囲は「全体向け」「フォロワー向け」「親しい友人向け」「一緒に旅行行った人向け」の4つ。

今の旅行には持ち主がおらず、**旅行のURLを知っている人なら誰でも見る・編集できる**（家族で共有しやすいように、そう作っていた）。このまま公開すると、見知らぬ人が旅行を書き換えられてしまうため、見る権限と編集する権限を分ける必要がある。

**決めたこと（interview-meで確認）**：
- **編集できるのは一緒に行った人**（招待リンクから参加した人）だけ。公開範囲は「見られる人」だけを決める
- **フォローは誰でもできる。承認制（鍵アカウント）も設定で選べる**（インフルエンサーは自由に、個人は承認制に）
- 「親しい友人」は、Instagramの「親しい友達」のように、自分でリストに入れた人
- **新しい旅行の初期値は「一緒に行った人向け」**。今ある旅行もすべてこの範囲にし、勝手に公開されないようにする
- 一緒に行った人以外には、**費用・精算と、一緒に行った人の名前（ゲスト参加者・記録した人）を見せない**

**設計**：
- **今の旅行のURL（trip.id）は、そのまま「招待リンク」**＝一緒に行った人の権限（見る＋編集）として扱う。家族の使い方は今までと変わらない
- 公開した旅行を他の人が見るときは、**別の公開用ID（trip.public_id）の、見るだけの画面**を使う。サーバーは見る人とその旅行の関係（フォロー・親しい友人・公開範囲）を確かめ、費用・名前を消してから返す。公開の画面から本物のtrip.idは漏らさない（漏れると誰でも編集できてしまうため）
- 公開範囲を変えられるのは旅行の持ち主（作った人。今ある旅行で持ち主がいないものは、参加しているアカウントが最初に「持ち主になる」）
- 公開の画面を出す前に、なりすまし対策（REQUIRE_SESSION、docs/adr/0005）をオンにしておく

**作る順番**：
1. 旅行の持ち主と公開範囲・公開用IDの列、見るだけの公開画面（費用・名前を消す）
2. プロフィール（名前・アイコン・ひとこと・承認制）、フォロー（承認制の申請・承認）、親しい友人のリスト
3. 公開範囲に応じた絞り込み：プロフィールの旅行一覧、フォロー中の人の新着、公開された旅の一覧
4. Appleの審査ガイドライン1.2のため、旅行・プロフィールそのものの通報とブロック（コメントには対応済み）
5. XやInstagramに共有したときのプレビューカード（OGP）

**まだ決めていないこと**：公開された旅の一覧の並び順（新着・人気）、検索（名前・場所）、プロフィールのURLの形。

### 持ち主と公開範囲（手順1）

- 旅行に`owner_account_id`（持ち主）・`visibility`（公開範囲）・`public_id`（公開用ID）を足した（migration 0034）。**今ある旅行はすべて持ち主なし・「一緒に行った人だけ」**。ログインして作る新しい旅行は、作った人が持ち主・初期値は「一緒に行った人だけ」
- **持ち主になる**：持ち主のいない旅行は、**最初に「参加する」を押したアカウント（`trip_members`で一番古い人）だけ**が「持ち主になる」を押せる（`POST /trips/:id/claim-owner`）。その人が参加をやめる・アカウントを消すと、次に古い参加者が最初の人になる。持ち主が決まるまで公開範囲は変えられない
- **公開範囲を変えられるのは持ち主だけ**（`PUT /trips/:id/visibility`、旅行の編集画面。選んだ時点で保存する）。初めて公開するときに公開用ID（`pub_`＋乱数）を作り、「一緒に行った人だけ」に戻しても同じIDを残す（再公開で同じリンクに戻る）。旅行の取得（`GET /trips/:id`）が返す公開用IDは、公開中のときだけ
- **編集は今までどおり旅行のリンク（trip.id＝招待リンク）**。公開範囲が決めるのは、別の見るだけの画面（`?p=公開用ID`）を誰に見せるかだけ

### 見るだけの公開画面（`GET /public/trips/:publicId`）

サーバーが、見る人と持ち主の関係（持ち主本人・承認済みフォロワー・親しい友人・ブロック）を確かめてから返す。判定表（`worker/src/visibility.js`の`canViewByVisibility`、クライアントのCoreに同じものがあり、テストで全組み合わせを突き合わせている）：

| 見る人 ＼ 公開範囲 | 一緒に行った人だけ | 親しい友人 | フォロワー | 全体 |
|---|---|---|---|---|
| 持ち主 | 公開画面は存在しない扱い（404） | 見える | 見える | 見える |
| 親しい友人 | 404 | 見える | 見える | 見える |
| フォロワー | 404 | 見えない | 見える | 見える |
| ログイン済みの他人 | 404 | 見えない | 見えない | 見える |
| ログインなし | 404 | 401 | 401 | 見える |
| 持ち主にブロックされた人 | 404 | 404 | 404 | 見える（ログインなしでも見られるため止めようがない） |
| 持ち主をブロックした人 | 404 | 404 | 404 | 404（自分で隠した相手） |

見られない人への返事は、公開の旅行の中身を一切含めない。ログインしていれば403に「持ち主の名前・アイコン・自分との関係」だけを付け（フォローを促すため）、ログインしていなければ401（ログインすれば見られるかもしれない）。**「一緒に行った人だけ」の旅行は、公開をやめた旅行も含めて404**（存在を知らせない）。

**出さないものは許可リスト方式**（`stripTripForPublic`）：決めた項目だけが出る。あとから列が増えても勝手に漏れない。

- 出す：旅行のタイトル・日程・旅行区分・サムネイル、予定（時刻・見出し・種類・移動手段と時間）、記録（エピソード・コメント・詳細・写真・動画・待ち時間・地図/お店/参考リンク・地図の座標と場所名）、移動の出発・到着地と会社・時刻、記録ごとの**評価の平均点と件数**、日ごとの場所・天気
- 出さない：**費用・精算**（costItems・settleUnit・移動の金額）、**一緒に行った人の名前**（ゲスト参加者・参加アカウントの一覧・記録した人 `author`）、**メール・評価した人の名前**、評価のレビュー本文（個人の評価で、名前と結びつくため。平均点だけ）、日ごとの音声の文字起こし・座標、作成/更新時刻
- **本物のtrip.idは一切返さない**。さらに、予定・記録・評価・日ごとのidも返さない（`PATCH/DELETE /blocks/:id・/entries/:id`は旅行IDを確かめずidだけで書き換えられるため、idがそのまま編集の鍵になる。公開画面には表示用の通し番号だけ）。テストで、返事の全文にtrip.id・各種idが含まれないことを確かめている
- **別行動（自分だけの道）**は、みんなの予定だけ出す。別行動の予定・記録と、誰がいつ別行動したかという分岐そのものは出さない
- いいね・コメントは**公開画面ではまだ付けられない（見るだけ）**。コメントを書いた人は旅行のメンバー側のアカウントで、その人たちの名前を公開してしまうこと、通報・ブロックの導線を公開側にも広げる作業が要ることが理由。次の段階で入れる
- 写真・動画のファイル自体（`/photos/:id`）は今までどおり、IDを知っていれば誰でも取れる（推測できない乱数）。公開をやめても、すでにIDを知っている人は画像だけは取れる点は、これまでと変わらない

### プロフィール・フォロー・親しい友人（手順2）

- **プロフィール**（migration 0035）：名前（`accounts.name`、40字・暴言チェック）・アイコン（既存の写真アップロードで`avatar_photo_id`。無ければ頭文字）・ひとこと（160字、`BANNED_WORDS`チェック）・承認制。プロフィールのURLは `?u=アカウントID`（6桁。公開用のハンドル名は作っていない）。プロフィールは**ログインした人にだけ**見せる
- **フォロー**：承認制でなければすぐフォロー中、承認制なら申請（承認待ち）→持ち主が承認／断る。フォローをやめる・申請の取り消し・フォロワーから外す。状態遷移は`nextFollowStatus`（none／pending／approved。同じ操作の繰り返しは冪等、できない操作は409）。承認制をやめると、承認待ちの申請は自動でフォローになる（Instagramと同じ）
- **親しい友人**：持ち主が**フォロワーの中から**選ぶ（Instagramの「親しい友達」と同じ。フォローしていない人は選べない）。フォロワーから外す・フォローをやめる・ブロックすると、親しい友人からも外れる。親しい友人はフォロワーでもあるので、フォロワー向けの旅行も見られる
- **人の見つけ方（今は検索なし）**：①旅行の「アカウント参加」の名前をタップ→プロフィール、②公開された旅行の持ち主の名前→プロフィール、③共有されたプロフィールのURL（`?u=`、プロフィールの「プロフィールを共有」）。**検索は未実装**（6桁のIDは数え上げられるので、プロフィールにはメール・プランなどを含めず、名前・アイコン・ひとこと・見せてよい旅行だけ返す。名前の検索を足すときは、ここを見直す）
- **プロフィールの旅行一覧**：その人の持ち主の旅行のうち、見る人に見せてよいもの（公開範囲の判定表と同じ）を、公開画面へのリンクのカードで出す。自分のプロフィールには全部の旅行を公開範囲のラベルつきで出す。**承認制のアカウントは、承認されたフォロワーにだけ一覧を見せる**（個別の公開用リンクは今までどおり有効）
- **Appleのガイドライン1.2（最小限）**：プロフィール・公開画面の「…」から**通報**（`POST /profiles/:id/report`。運営者へメール、24時間以内に確認。通報したあとブロックも案内）と**ブロック**（既存の`/user-blocks`を共用）。ブロックすると互いのフォロー・親しい友人が外れ、**ブロックされた人はあなたをフォローできず、非公開（フォロワー・親しい友人）の旅行は見えず、あなたのプロフィールは見えない**（404）。ブロックした側には相手のプロフィールが「ブロック中」の最小限だけ出て、そこから解除できる

### オーナーの追加の決定（2026-10-01）

- **フォロー数・フォロワー数は、他の人には初期値で見せない**（小さな家族・友達グループの利用が中心で、数が少ないと寂しく見えるため）。他の人のプロフィールには、名前・アイコン・ひとこと・見せてよい旅行・行ったことある旅先（設定による）・フォローのボタンだけ。**自分のプロフィールでだけ、数と一覧（フォロー中・フォロワー・承認待ち・親しい友人）が見える**。インフルエンサー向けに、プロフィールの設定「フォロワー数をプロフィールに表示する」（`show_counts`、初期値オフ）をオンにすると、他の人にも**数だけ**見える（一覧は本人にしか返さない）。サーバーが返すかどうかで決めており、画面で隠しているだけではない（テストあり）
- **「行ったことある旅先」をプロフィールに出す**：国（海外）と都道府県の**名前だけ**（どの旅行か・いつかは返さない）。マイログの「行ったことある旅先」と同じ集計（`getVisitedPlaces`。参加した旅行が対象で、本人が旅行ごとに「外す」にした場所は出ない）を、**読むだけモード**で使う：D1に保存済みの`map_admin1/map_country`とday_infosだけで集計し、**逆ジオコーディング（Nominatim）も書き戻しもしない**ので、他の人がプロフィールを開いてもサブリクエストは増えない（上限50に対して十数回）。まだ地域が解決できていない地点は、その人が自分のマイログを開いたときに少しずつ埋まるまで出ない。画面では国を大陸ごと・国旗つき、都道府県を地方ごとに並べる。公開範囲は設定「行ったことある旅先をプロフィールに出す」（`visited_visibility`）で**全体／フォロワー／出さない（初期値：フォロワー）**。サーバー側で判定し（`canViewVisited`）、フォロワーでない人には中身を返さず「フォロワーにだけ公開」という印だけ返す。ブロックしている・されている人には、プロフィールごと見えない。本人にはいつでも見える（設定を確認できるように）

## 追記（2026-10-01 SNSなし）：出したのは「見るだけの公開リンク」だけ。SNSは保留

**オーナーの決定**：当面SNSはやらない。セトログのような、個人・家族の記録アプリとして出す。そのため、上の手順1〜2のうち**プロフィール・フォロー・親しい友人・プロフィール通報は出さない**（コードは残すが、画面からも、サーバーのルートからも使えない）。出すのは**リンクを知っている人だけが見られる、見るだけの公開リンク**だけ。

**出したもの**
- 公開範囲は2つだけ：「一緒に行った人だけ」（初期値）と「リンクを知っている人（見るだけ）」（値は`public`）。一覧・検索・おすすめはどこにも無いので、実質は限定公開（unlisted）。親しい友人・フォロワーの値は`PUT /trips/:id/visibility`で**400 `visibility_unavailable`**を返す（`worker/src/visibility.js`の`ENABLED_VISIBILITIES`に足せば通る）
- **入り切りできるのは、その旅行にアカウントで参加している人（`trip_members`）なら誰でも**。持ち主になる手順は不要（ゲスト参加者・未参加・ログインなしは不可。サーバーがセッションで確かめる）。`owner_account_id`は、空のときだけ最初に公開した人を記録する（将来のために列は残すが、可否の判定には使わない）
- 旅行の編集画面の「見るだけのリンク」：スイッチ（オンにするときは確認）、リンクの表示、共有（`navigator.share`→クリップボード→コピー用の欄、本文は「旅の足跡で旅行を見てね」＋URL）、「見え方を確かめる」。「メンバーを招待」（編集もできる）との違いを文章で書いてある。オフにしても`public_id`は残り、もう一度オンにすると同じリンクに戻る
- 公開の画面（`?p=`）：ログイン不要。持ち主・フォロー・ブロックによる出し分けはやめ、見る人で内容は変わらない（許可リスト方式の`stripTripForPublic`は上のまま。費用・精算、同行者の名前、記録した人、評価のコメント、別行動の予定、本物のtrip.id・各種idは出ない）。持ち主の表示・フォローのボタン・ログインを促す門前払いの画面は無い。最後に「旅の足跡で作った旅の記録です」とアプリへのリンク。公開の画面での「地図でふりかえる」は、地図の再生がログイン中の旅行の状態に強く結びついているので、**今回は見送り**
- サーバーのSNS系ルート（`/profiles/*`・`/follows/*`・`/me/profile`・`/me/connections`・`/me/follow-requests/*`・`/me/followers/*`・`/me/close-friends/*`・`/trips/:id/claim-owner`）は、`index.js`の定数`SOCIAL_ENABLED = false`のあいだ**410 `feature_disabled`**を返す。クライアントの同名スイッチは`app.js`の`SOCIAL_UI`。プロフィール画面・フォロー・親しい友人・プロフィールの通報/ブロック・メンバー名からプロフィールへのリンクは、画面から入れない

**必要なマイグレーションは0034だけ**（trips の3列と2つのindex）。**0035（プロフィール・フォロー・親しい友人・通報のテーブルと列）は、SNSを復活させるまで流さなくてよい**。Workerは0035のテーブル・列が無くても動く（テストで、SNSのテーブルを作らない状態で全部通している）。

**SNSを復活させるとき**：①`SOCIAL_ENABLED`と`SOCIAL_UI`を`true`に、②0035を流す、③`ENABLED_VISIBILITIES`（サーバー）と`ENABLED_VISIBILITY_KEYS`（Core）に`close_friends`・`followers`を足し、公開の画面を元の判定表（この追記より上の表）に戻す。③の元の実装は、このブランチの手前の`feat/tabilog-follow-visibility`（b860aa1）にある。**手順3以降（公開された旅の一覧・フォロー中の新着・検索・OGP）は未着手のまま**。
