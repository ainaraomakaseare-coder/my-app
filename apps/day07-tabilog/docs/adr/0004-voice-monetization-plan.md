# 音声入力（AI機能）を有料化する方針

音声入力はこのアプリで唯一AIを呼び出す機能で、使うたびにOpenAIへの実費が発生する。無料のまま公開範囲が広がると、利用が増えるほど赤字が拡大するリスクがあるため、有料化の方針を`interview-me`で確認した。

**決めたこと**：
- 無料プランでは音声入力機能そのものを使えなくする（他の機能は今まで通りすべて無料）
- 支払うのは旅行を作った人（幹事）で、参加者ではない
- 価格は月額のサブスクリプション制。ベーシック（月300円・月10回まで）／プレミア＋（月1000円・月50回まで）の2段階
- サブスクに入らなくても、回数券（買い切り500円・10回分）で単発利用できる
- どのプランでも**1回の録音は3分まで**というアプリ側の制約を必ず伴わせる。これにより「1回あたりの実費」の上限が決まり、上限回数を全部使い切っても赤字にならない価格設定ができる（時間の上限を外すと、長時間の録音で実費が予測できなくなるため、プレミア＋でも時間の上限だけは変えない）
- 決済はStripeを使う（サブスクリプション管理・買い切り決済の両方に対応させる）

**見送ったこと**：
- 参加者ごとに個別課金する方式（今のゲスト参加者＝ログイン不要という設計と相性が悪いため）
- 音声以外の機能（写真・旅程作成など）の有料化（今回のスコープ外）
- 本番運用に向けた税務・インボイス対応（Stripe本番切り替え時に別途検討）

**未着手**：Stripeのアカウント登録・テストモードでのサブスク実装・回数制限のサーバー側実装。まず外部サービスに依存しない「1回3分で自動的に録音を止める」機能だけ先行して実装した（`docs/adr`本文と`CONTEXT.md`の「音声からの記録作成」参照）。

## 後日の変更（DAY26〜）

- 無料プランでも月2回までは音声入力を使えるようにした（「無料プランでは使えない」から変更。有料プランへの入り口として月2回だけ体験できる形にした方が良いと判断）
- 新規登録時の回数券3回分ボーナスは維持する（機能の良さを知ってもらうための特典なので残したい、という判断）。ただし、アプリ内に自己サービスのアカウント削除機能（Appleのガイドライン5.1.1(v)対応）を追加したことで、「削除→同じメールで再登録」を繰り返すだけで特典を無限に得られる抜け道が一時的に生じたため、以下の対策をセットにした
- アカウント削除は`accounts`の行をDELETEせず、名前・プラン・回数券などの個人情報だけを空にするUPDATEにする。emailの行自体は残すことで、再登録時に`getOrCreateAccount()`が「既存アカウント」と判定し、新規登録特典の再付与を防ぐ
- 同じ理由で、アカウント削除時に無料プランの月間上限（`voice_uses_this_period`）もリセットしない（削除→再登録を繰り返すだけで無料プランの月2回を何度でも復活させられてしまうため）。月が変わったときの通常のリセットは`resetPeriodIfNeeded()`が別途行う

## メモの取り込み（2026-09-26〜）

「メモから記録する」を無料でも使いやすくした。
- **決まった形のメモはAIを使わない**：「10時 新宿」のように時刻で始まる行＝予定、その下の行＝記録、「2日目」「4/2」の行＝日付の切り替え。アプリ側（Core.parseMemo）で分けて `POST /trips/:id/memo-blocks` で保存する。AIの費用がかからないので、ログインも回数も要らない（何回でも無料）
- **形が崩れたメモはAIで整理**し、音声とは別の「メモの枠」を使う（accounts.memo_uses_this_period）。月の回数は 無料10・ベーシック30・プレミア＋100（MEMO_MONTHLY_LIMIT）。有料プランは、以前（音声と共通の枠で10・50）より減らないようにした。枠を使い切ったら回数券を使う
- 音声・AIで整理のときだけ、ログイン・AIへの送信の同意・回数を確かめる（以前は画面を開く時点で求めていたので、回数が無いとメモも使えなかった）

## 無料プランの音声入力を月2回→月10回に引き上げ（2026-09-28）

docs/adr/0012で試作したCloudflare Workers AIへの文字起こし切り替えを本番採用した（詳細は0012の追記参照）。文字起こしの実費がほぼ無料になったため（整理（`organizeTextIntoBlocks`）は引き続きOpenAIを使うので実費はゼロではない）、無料プランの月間上限（`PLAN_MONTHLY_LIMIT.free`）を月2回から月10回に引き上げた。有料プランが無料プランを下回らないよう、basicも10回→20回に上げている（premium_plusは50回のまま）。新規登録時の回数券3回分ボーナスは変更なし。

## 有料プランの販売をいったん止める（2026-09-30、App Review 3.1.1）

**決定**：ベーシック（月300円）・プレミア＋（月1000円）・回数券の販売を、Web版・iOSアプリの両方で**いったん全部止める**。全員が同じ無料の回数（音声入力 月10回・メモ／スクショのAI整理 月10回）を使う。上の各節（有料化の方針・回数券・プラン別の上限）は、復活させるときの設計資料として残す。

**きっかけ**：App Reviewが2回続けて Guideline 3.1.1 で却下した。「アプリ内課金の仕組みを実装しないと、アプリの外で買った有料コンテンツにアプリからアクセスできてしまう」という指摘。iOSアプリ内では購入ボタンを隠していた（`isNativeApp()`）が、Webで Stripe 払いしたプラン・回数券の上限がiOSアプリにも効いてしまう作りだったため、「外で買ったものをアプリで使える」と判断された。実際には Stripe で払った人は誰もいなかった。

**やったこと**
- Worker：`effectivePlan(account)`（`worker/src/index.js`）が、DBの`plan`列に何が入っていても常に `'free'` を返す。回数の確認（`checkVoiceQuota`）と `/accounts/ensure` の返す上限・`plan` はこの関数を通る。使い切ったときの理由は `premium_required` ではなく `quota_exceeded` だけにした。
- `/billing/checkout`・`/billing/portal`・回数券の購入（`/billing/ticket*`）は **410 `{"error":"billing_disabled"}`**。`/billing/webhook` は経路を残して **何もせず200**（Stripeの再送を止めるため。アカウントは変わらない）。切り替えは `BILLING_ENABLED = false`。
- **おまけの回数（`ticket_credits`）**：新規登録の特典（3回分）は購入ではない無料の回数なので、今までどおり、月の枠を使い切ったあとに1回ずつ消費する。購入で増える経路（Stripe Webhook・回数券の購入）は上のとおり全部止まっているので、有料で増えた回数は存在しない。画面では「おまけの回数：○回」と呼ぶ。
- フロント：プランを選ぶボタン・「プランを見る」・支払い管理へのリンク・回数券・プラン名バッジ（ベーシック／プレミア＋）を全部外した。プロフィールと音声・メモ・スクショの画面は「あと○回（月10回まで）」だけを出す。使い切ったら「今月の回数を使い切りました。来月1日にまた使えます」（購入への案内は無し）。`Core.canUseBranches` は常に true のまま（コメントだけ更新）。
- `privacy.html` に、現在は有料の機能が無くお支払い情報は取得しないことを追記。iOSアプリは `webDir: ../day07-tabilog` で同じファイルを同梱するので、別のコピーは無い。Capacitorの `allowNavigation` から Stripe のホストも外した。

**復活させるとき**（Appleのアプリ内課金＋RevenueCat を想定）：(1) `effectivePlan` を、アプリ内課金の状態（RevenueCatのWebhookで`plan`列を更新する）を見て `'basic'`／`'premium_plus'` を返す形に戻し、`BILLING_ENABLED` を見直す。(2) 購入導線はiOSアプリではApple課金だけにする。Webで買った分をiOSで使わせる（リーダー系）のは別途審査要件を確認する。(3) Stripe関連のコード（`createCheckoutSession`・`createPortalSession`・`handleStripeWebhook`）はWorkerに残してあるので参考にできる。画面側の購入UI（旧 `PLAN_OPTIONS`・`startCheckout`）は削除済みなので、git履歴（2026-09-30より前）から拾う。

## 次のアップデートでアプリ内課金にする（2026-09-30 決定）

**決定**：審査中のビルド103（1.1.0）は課金なしのまま通す。有料プランは次のアップデート（1.2.0）で、Appleのアプリ内課金（RevenueCat経由）として復活させる。Stripeを主な決済手段にするのはやめる。

**理由**：iOSアプリの中でアプリ内課金を買えるようにしておけば、審査で3.1.1に当たらない。1.1.0に混ぜると、また3.1.1で止まる危険があるので分ける。

**着手前に決めること**
- 値段とプランの構成（上の節の案：ベーシック月300円・月20回、プレミア＋月1000円・月50回、回数券500円で10回分）をそのまま使うか
- Web版でも売るか。売る場合、StripeでWeb購入した分をiOSでも使わせてよいのは、iOSアプリ内でも同じものをアプリ内課金で買える場合だけ（ガイドライン3.1.3(b)）

**着手前にオーナーがやること**
- App Store Connect：有料アプリ契約・口座・税の登録。小規模事業者プログラムへの申請。サブスク（自動更新）と回数券（消耗型）の課金アイテムの作成
- RevenueCatのアカウント作成と、App Store Connectとの連携

**実装の範囲**：上の「復活させるとき」に加えて、iOSアプリの購入画面に「購入を復元」ボタン、自動更新の説明、利用規約・プライバシーポリシーへのリンクを置く（ガイドライン3.1.2）。`tasks/todo.md` はStripe前提の計画なので、着手時にアプリ内課金前提で書き直す。

## 無料枠を月3回にし、有料は回数券だけにする（2026-09-30）

- 無料の月間上限を、音声入力・メモ／スクショのAI整理ともに**月10回→月3回**に下げた（`PLAN_MONTHLY_LIMIT.free`・`MEMO_MONTHLY_LIMIT.free`）。無料ユーザーが1万人規模になったとき、無料枠のOpenAIの実費を回数券の売上でまかなえなくなる試算になったため。新規登録の特典（おまけの回数3回分）は変えない
- 1.2.0の有料は**月額サブスクをやめて回数券（消耗型のアプリ内課金）だけ**にする。買った回数は `ticket_credits` に足し、無料枠を使い切ったあとに消費する（おまけの回数と同じ）。値段は次のとおり（2026-09-30決定）
  - `com.hiroyaapps.tabilog.ticket10`：10回 500円
  - `com.hiroyaapps.tabilog.ticket30`：30回 1,200円
- 回数券に有効期限は付けない。アカウントを削除すると残りの回数も消えるので、削除画面でそのことを知らせる
- 決済はRevenueCat経由のアプリ内課金。RevenueCatのWebhookで購入を受け取り、`ticket_credits` に足す（同じ取引を二重に足さない）。最初はiOSアプリだけで売り、Web版では売らない

## 回数券のアプリ内課金の実装メモ（2026-09-30）

上の「無料枠を月3回にし、有料は回数券だけにする」を実装した（ブランチ `feature/tabilog-iap-tickets`。1.2.0で出す想定。審査中の1.1.0には入れない）。

- **Worker**：`POST /billing/revenuecat-webhook`。`NON_RENEWING_PURCHASE`だけを処理し、商品→回数の表（`IAP_TICKET_PRODUCTS`）で回数を決めて`ticket_credits`に足す。二重加算は、処理した`transaction_id`を`iap_transactions`（主キー）に記録し、記録と加算を1つのbatchで行って防ぐ。認証は`Authorization`ヘッダーと`REVENUECAT_WEBHOOK_AUTH`の一定時間比較（未設定なら404）。`SANDBOX`は`REVENUECAT_ACCEPT_SANDBOX="true"`のときだけ反映する。`effectivePlan`・月の回数・プラン（すべて`free`）は変えていない。Stripe系の経路は410／何もしないままにした。
- **RevenueCatの利用者ID（`app_user_id`）は`accounts.account_id`**（サーバーが採番する6桁）。理由：①サーバーがこの人を指すのに使っている変わらない番号で、ログイン方法（Google／Apple／メール）を変えても同じ。②メールアドレスや名前をRevenueCatに渡さずに済む。③メールアドレスは利用者が別のものでログインし直せるうえ、個人情報になる。アカウントを削除しても`accounts`の行は残る（`deleteAccount`はUPDATEで空にするだけ）ので、IDは再利用されない。6桁は推測できるが、IDを知っても他人の回数を増やせる経路は無い（回数が増えるのは、そのIDで実際に購入が成立したときだけ）。
- **未知のユーザー・未知の商品は200で返す**（ログだけ残す）。再送しても直らない失敗で500を返すと、RevenueCatが再送を繰り返すため。ログインしてからしか買えない作りなので、未知のユーザーはRevenueCatの匿名ID（ログイン前の購入）くらいしか無く、その場合は取引IDのログを見て手で足す。DBの書き込みに失敗したときだけ500にして再送させる。
- **iOSアプリ**：`@revenuecat/purchases-capacitor`（Capacitor 6対応の9.x）。公開SDKキーは`app.js`の`REVENUECAT_IOS_API_KEY`（空なら購入画面ごと隠す）。ログイン後に`Purchases.logIn(accountId)`、ログアウト時に`logOut`。購入画面はプロフィールと、音声・メモ・スクショの回数を使い切った状態にだけ出し、値段はStoreKitの表示用文字列を使う。購入後は`/accounts/ensure`を数回取り直して反映を待つ。**Web版には購入の画面も案内も出さない**（3.1.1）。
- アカウント削除の確認に、残っている回数券は消えて払い戻しできないことを追記した（残りがあるときは回数も出す）。
- `privacy.html`に、お支払いはAppleが処理すること、購入記録（アカウントID・商品・取引ID）がRevenueCat, Inc.経由で届くこと、カード情報は受け取らないことを追記した。
- **やっていないこと**：返金（`CANCELLATION`／`REFUND`）で回数を戻す処理（消耗型は返金されても使い終わっていることがあるため。必要になったら別に決める）。プランの再開。
