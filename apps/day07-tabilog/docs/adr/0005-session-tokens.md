# ログイン後の本人確認をセッショントークンにする

これまでサーバーは、アプリが送ってきたメールアドレスをそのまま「本人」とみなしていた。メールOTPでメールの持ち主であることは確かめていたが、その後の操作ではメールアドレスしか送られないため、**他人のメールアドレスを知っていれば**、その人のアカウント削除（`/accounts/delete`）・支払い管理ページ（`/billing/portal`）・評価・マイログの閲覧ができてしまっていた。家族だけで使っているうちは実害が出にくかったが、いいね・コメント（docs/adr/0006）で知らない人同士が同じ旅行に書き込むようになる前に直す必要があった（2026-09-25）。

**決めたこと**：
- メールOTPの確認（`POST /auth/email/verify`）に成功したら、サーバーがセッショントークン（32バイトの乱数、16進64文字）を発行する。有効期限は180日
- アプリはトークンを`tabilog:user`に保存し、すべての通信に`Authorization: Bearer <token>`で付ける
- DBの`sessions`テーブルにはトークンそのものではなくSHA-256のハッシュだけを置く（DBが漏れてもなりすませない）
- メールアドレスを受け取っていた処理（評価・マイログ・アカウント・支払い・参加・AIによる記録作成）は、すべて`resolveEmail()`を通す。トークンがあればそれが正で、送られてきたメールアドレスと食い違えば403で拒否する
- ログアウト（`POST /auth/logout`）とアカウント削除で、サーバー側のセッションも消す

**移行期間の扱い**：審査中・配布済みのiOSアプリ（1.0.1まで）はトークンを送らない。いきなりトークン必須にすると、審査中のアプリでアカウント削除ができなくなり、審査に落ちる。そのため当面は「トークンが無ければ、送られてきたメールアドレスを使う」従来の動きを残す。1.1.0以降が行き渡ったら、`wrangler.jsonc`の`vars`に`"REQUIRE_SESSION": "1"`を足して`wrangler deploy`すると、トークン必須に切り替わる（コードの変更は不要）。それまでは上記の抜け穴が残ることを承知しておく。

**見送ったこと**：
- Google/Appleログインのサーバー側検証（id_tokenの署名確認）。今はどちらもクライアントIDが空で使われていないため。有効にするときは、トークンを発行する前にサーバーでid_tokenを検証する処理を足すこと（今のままではトークンが発行されない＝いいね・コメントができない）
- 既存のログイン済みの人への自動移行。トークンを持っていない人は、いいね・コメントしようとしたときに「もう一度ログインしてください」と案内する

**移行後にやること**：旅行を開くと、評価（ratings）ごとに評価した人のメールアドレス（raterEmail）が、リンクを知っている人全員に返っている。古いアプリが「自分の評価」を見分けるのに使っているため今は残しているが、REQUIRE_SESSIONをオンにするときに、サーバー側でトークンから「自分の評価か」を判定して返す形に変え、メールアドレスは返さないようにする。
