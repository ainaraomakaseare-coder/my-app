# スクショから予定を作る（航空券・ホテル予約・チケット・レシートの画像から、予定の候補を作る）

旅行の予定は、予約サイトやアプリの画面（航空券のeチケット、ホテルの予約確認、新幹線のEX予約、Googleマップの乗換案内、野球や漫才劇場のチケット、レシート）にすでにそろっている。それを見ながら手で打ち直すのは面倒なので、**スクリーンショットを最大10枚まとめて選ぶと、予定（Block）と記録（Entry）の候補を作り、確認画面で直してから保存できる**ようにした（2026-09-30、オーナーの方針）。

## 決めたこと

**方式A（文字を先に読む → 整理する）**：

1. 画像 → **Cloud Vision の `DOCUMENT_TEXT_DETECTION`** で文字にする。全画像を**1回の `images:annotate` にまとめる**（Visionは1リクエスト16枚まで。こちらの上限は10枚なので必ず1回）。
2. 文字 → **OpenAI（既存の整理役と同じモデル）** に、予約・チケット・レシート向けの新しいプロンプトと厳密なJSONスキーマ（`strict`）で予定の候補にしてもらう。
3. 場所の名前 → **Google Places API (New) の Text Search** で座標まで探す（1つの名前につき1回、**最大12回**）。会場・宿のリストをコードに持たず、画像に書かれた名前（または、会場名が書かれていないときにAIが確実だと判断した会場名）をそのまま検索する。
4. 確認画面に返す（**ここでは何も保存しない**）。
5. 「この内容で追加」で保存（AIを使わない別のエンドポイント、1回のD1バッチ）。

方式B（画像をそのままOpenAIに渡す）は、画像のトークン代が高く、写り込んだ氏名・予約番号をOpenAIに画像のまま渡すことになるため採らなかった。方式Aなら、文字だけがOpenAIに渡り、プロンプトで「予約番号・氏名・電話番号・メール・カード番号は書かない」と指示できる。

### エンドポイント

| | 役目 | AI | ログイン | 回数 |
|---|---|---|---|---|
| `POST /trips/:id/screenshot-scan` | 画像→候補（何も保存しない） | 使う | 必須（`resolveEmail`） | **メモのAI整理の枠を1回**（画像が何枚でも1回。成功して候補が1件以上あったときだけ消費。`memo_uses_this_period`、使い切ったら回数券） |
| `POST /trips/:id/screenshot-blocks` | 確認後の保存 | 使わない | 不要（`/memo-blocks`と同じ扱い） | 使わない |

- リクエスト（scan）：`{ images: [{ type, data(base64) }], email }`。**マルチパートにせずbase64のJSON**にした（iOSアプリのネイティブ通信経路`nativeApi`はJSONボディだけが安定して送れるため。写真アップロードの`postBinary`のようなバイナリ経路を新しく作らない）。
- レスポンス（scan）：`{ items, unreadable, dropped, usage }`。`items`は確認画面の候補、`unreadable`は「読み取れなかった画像」（画像番号は0始まり＋理由）、`dropped`は候補にできなかった件数。
- 保存（blocks）：`{ items, author }`。**サーバーは確認画面の値をそのまま信用せず、`validateSaveItems`で検証し直す**（日程の外の日付・見出しが空・日付が壊れているもの・Google以外の地図URL・座標の範囲外は落とす。正しい項目だけ保存して`errors`で返す）。予定と記録は**1つのD1バッチ**（途中で失敗して「予定だけ残る」事故を防ぐ。2026-09-15の教訓）。新しいマイグレーションは**作っていない**（既存の`entries.map_lat`等の列・`travel`列を使う。`map_place_name`列が無い古いDBは列なしで保存し直す）。

### 何を取り出すか

1件＝1つの出来事。往復は2件、乗り換えのある経路は区間ごとに1件（徒歩は作らない）。

| 画像 | 予定の中身 |
|---|---|
| 航空券・新幹線・電車・バス | `category=transport`、`transport`（plane/shinkansen/train/bus/…）、見出し「羽田→那覇 JAL903」、ブロックの時刻＝出発時刻、`travel`に区間・会社と便名・出発/到着時刻、**ブロックの地図＝出発地、`travel.arriveMapUrl/arriveLat/arriveLng`＝到着地**（アプリが既に持っている項目。到着地の地図は次の予定のタイムゾーン決定に使われる。`docs/adr/0009`）、費用は`costItems` |
| ホテル | `category=lodging`、見出し＝宿の名前、チェックイン時刻、宿の場所。**チェックアウト日までの泊数ぶん（最大14泊）の予定に展開**（旅行詳細の「宿泊先」は泊ごとの予定で数えるため。費用は1泊目だけ） |
| チケット（野球・漫才劇場など） | `category=sightseeing`、見出し＝イベント名、開演時刻、会場（検索名）、チケット代 |
| レシート | `category=food`、店名、時刻、品目ごとの費用。**`receipt-parse.js`のルールベース解析で取れた品目を、AIへの「参考」として添える**（画像のOCR文字を優先するよう指示） |
| Googleマップの乗換案内 | 区間ごとの移動（出発・到着の駅、時刻、運賃） |

- **日付**：年が書かれていなければAIは`--MM-DD`で返し、**旅行の日程から年を補う**（`resolveDate`。開始日・終了日の年を候補に、日程の中に入る年を選ぶ。年をまたぐ旅行の1/1は翌年）。日付がまったく読めなかった候補は旅行の初日に置いて警告する（黙って捨てない）。日程の外の日付は警告し、直すまで追加できない。
- **チェックイン時刻**：写っていなければ**15:00**。ただし、同じ日に到着する移動（到着日がその日）の到着時刻が15:00より遅ければ、**いちばん遅い到着の60分後**（例：18:05着なら19:05）。24時はこえない。目安の時刻には確認画面で「（目安）」と出す（`applyCheckInDefaults`）。翌日着（1:30着など）は15:00のまま。
- **タイムゾーン**：文章から推測しない。時刻は写っているそのままの現地時刻として入れ、**ピン（地図の場所）が時差を決める**既存のルール（`docs/adr/0009`）に任せる。
- **費用**：日本円が既定。外貨は`currency`（ISO 4217）付きで受け、保存の直前にクライアントが`/rates`からレートを付ける（`docs/adr/0014`、`docs/adr/0015`と同じ`fetchRatesForImportBlocks`）。マイナス（割引）の行は入れない（既存の費用の検証が0以上のため）。
- **個人情報**：予約番号・搭乗者や宿泊者の氏名・電話・メール・カード番号は、プロンプトで書かないよう指示し、確認画面にも保存にも入らない（テストで確認）。座席などの補足（`note`）は記録のひとこととして入れる。

### 確認画面

日ごとにまとめ（`Core.groupScreenshotItemsByDay`）、各候補に「追加する」のオン／オフ、元の画像のサムネイル、日付・時刻・見出し・種類・場所・費用の編集欄を出す。場所は「変える／場所を探す」で、既存の`/places/search`と`/places/details`（記録フォームの「場所名で検索」と同じ）から選び直せる。「地図を外す」もできる。読み取れなかった画像は末尾の「読み取れなかった画像」に、サムネイルと理由（文字が見つからない・読み取りに失敗・使える情報がない）を出す。追加を押すと`Core.screenshotItemsToSavePayload`が日付・見出しを先に確かめ、問題があれば直すまで送らない。

### AI送信の同意

音声・レシートの同意（`tabilog:ai-consent`）とは**別のキー（`tabilog:ai-consent-screenshots`）**で確認する。スクリーンショットには氏名・予約番号・電話番号が写りやすく、音声・レシートと送るものの性質が違うため、その旨と「写したくない部分は隠してから選ぶ」ことを同意の文面に書いた（Appleのガイドライン5.1.1(i)/5.1.2(i)対応の延長）。

### 画像の縮小

クライアントで長辺1600px・JPEG品質0.8に縮めてから送る（`fileToCompressedBlob`、レシート・写真と同じ関数）。1枚あたり300〜700KB程度。サーバーの上限は、1枚のbase64が150万文字、全体で900万文字（Visionのリクエスト全体の上限10MBに収めるため）。超えたら`invalid_size`。

## サブリクエストの見積もり（Workers Freeは1リクエスト50回まで）

`estimateSubrequests`（`screenshot-import.js`、テスト済み）で数えている。

| 内訳 | 回数 |
|---|---|
| Cloud Vision（全画像を1リクエスト） | 1 |
| OpenAI（切れたときだけ「考える量を減らして」もう1回） | 1（最大2） |
| 場所検索 Text Search（名前ごとに1回、同じ名前は1回、上限） | 最大12 |
| D1（ログイン確認・回数の確認と消費・旅行の取得など） | 約10と見積もる |
| **合計** | **約24（最大でも約35）** |

場所検索が12件を超える分は検索せず、地図なしで確認画面に出す（本人が「場所を探す」で選び直せる）。検索の優先順は、宿・会場・店 → 移動の出発地 → 移動の到着地。場所検索は既存の`googleTextSearchPlace`（IDを取ってから詳細を取る2回構成）ではなく、**FieldMaskに`location`を含めて1回で座標まで取る**新しい`googleTextSearchOne`を使う（サブリクエストを名前ごとに1回に抑えるため。2回構成だと最大24回になる）。`POST /screenshot-blocks`は、D1（旅行の取得・バッチ・更新）の3回程度で、Vision・OpenAI・Placesは呼ばない。

## 費用の見積もり

- **Cloud Vision**：`DOCUMENT_TEXT_DETECTION`は**月1,000枚まで無料、超えたら1,000枚あたり約$1.5**。1回の取り込み（最大10枚）で最大10枚使う。全部使っても1回$0.015。**GCPのクォータでオーナーが設定したVisionの1日の上限（例：30枚/日、`docs/adr/0011`）は、10枚の取り込みだと3回で尽きる。この機能を出す前に、1日の上限を引き上げるか、上限に達したときの表示（`vision_failed`）を許容するか決めること。**
- **Google Places Text Search**：`places.displayName`・`places.formattedAddress`・`places.location`を聞くのは Text Search **Pro** の単価帯（IDだけのEssentialsより高い。**月5,000回まで無料、超えたら1,000回あたり約$32**。2026-09-30時点の記憶による数字で、公式の料金ページで要確認）。1回の取り込みで最大12回。月5,000回の無料枠なら、12回使い切る取り込みでも約400回/月まで無料。もっと安くしたいときは、IDだけ取って`places/{id}`のDetails Essentials（`location`のみ、月1万回無料）に切り替える手があるが、サブリクエストが倍になる（最大24回）ため採らなかった。
- **OpenAI**：1回の取り込みは、**入力＝プロンプト約1,500トークン＋OCR文字（1枚あたり最大4,000文字。旅の画面は多くが数百〜2,000文字。10枚で最大約2万トークン）、出力＝候補1件あたり約200〜300トークン（10件で約3,000トークン）＋考える分（`reasoning: medium`）**。この機能を使う1回のトークン数は、音声の整理（文字起こし数千文字）より入力が大きくなりうる。**単価はOpenAIの料金ページのモデルごとの値で決まり、このリポジトリには記録が無いので、金額は推測しない**（実際の使用量はOpenAIの利用状況ページで、この機能を数回使ってから確認する）。メモのAI整理と同じ枠（月10回まで無料）に入れたのは、1回あたりの費用がメモの整理と同じ桁のため。
- 枠を「画像の枚数」ではなく「1回の取り込み」で数えるのは、オーナーの方針（最大10枚で1回）。無料枠を使い切ると回数券を1回使う。

## 避けたこと

- **画像をそのままOpenAIに渡す**（方式B）。上の理由。
- **会場・空港・駅のリストをコードに持つ**こと（野球場・劇場など）。画像に書かれた文字（またはAIが確実だと判断した会場）を場所検索する。推測した場合は`placeGuessed`で警告を出して確認してもらう。
- **確認なしで保存する**こと。`docs/adr/0002`の音声は確認画面を挟まないが、こちらは画像の文字の読み間違い（日付・金額）がそのまま予定に残るリスクが高いため、`docs/adr/0015`（JSON貼り付け）と同様に必ず確認画面を挟む。
- **新しいDBのマイグレーション**。他のブランチが0030・0031を追加している。この機能は既存の列だけで足りたので作っていない（もし必要になったら0032にする）。
- **日付が読めない候補を捨てる**こと。旅行の初日に置いて警告し、本人に直してもらう。

## 2026-09-30追記：音声・メモ（AI／決まった形）も同じ候補づくりと確認画面にした

オーナーの要望：音声入力と「メモから記録する」も、スクショと同じように**時刻・費用（金額・通貨）・場所（地図のピン）を、分かるときだけ入れ**、**同じ確認画面**を通してから保存する。分からないことは無理に埋めず空欄のままにする。

### 共有の候補づくり

3つの取り込みは、同じ形の候補（日付・時刻・見出し・種類・移動手段・出発地/到着地と時刻・費用・場所・記録のひとこと）を作り、同じ検証と場所検索を通る。

| | 入力 | 候補を作る所 | 場所 | 枠 |
|---|---|---|---|---|
| スクショ | 画像 | Vision→OpenAI（`screenshot-scan`） | 自動で検索（最大12回） | メモの枠 |
| 音声 | 録音 | 文字起こし→OpenAI（`voice-scan`） | 自動で検索（最大12回） | 音声の枠 |
| メモ（AI） | 貼り付け | OpenAI（`text-scan`） | 自動で検索（最大12回） | メモの枠 |
| メモ（決まった形） | 貼り付け | ブラウザだけ（`Core.parseMemo`→`Core.memoBlocksToProposals`） | **自動では探さない**。確認画面の「場所を探す」で本人が探す | 使わない（無料） |
| 自分のAIの答え（JSON） | 貼り付け | ブラウザだけ（`Core.parseImportedBlocksJson`→同上） | 同上 | 使わない |

- **検証と補正は1つ**：`screenshot-import.js`の`normalizeProposalItems`（`normalizeScreenshotResult`はその薄い呼び出し）。ctxで動きを切り替える：音声・メモは`fixedDate`（「この日」はAIの日付を見ず固定）／`allowedDates`（複数日・別行動の日々。外れた日付は初日に置いて警告）／`allowGuess:false`（会場を推測しない）／`checkInDefaults:false`（宿の時刻が無くても15:00を作らない＝**分からない時刻は空のまま**）／`noteMax:1000`／`maxItems:60`。時刻の形が壊れたもの・マイナスや文字の金額は捨てて空にする。
- **プロンプトと出力スキーマ**：`worker/src/import-proposals.js`の`buildProposalPrompt`／`proposalSchema`。時刻は「10時に」のように具体的に話されたときだけ、金額は「ランチ1500円」のように話されたときだけ（外貨は`currency`）、場所は具体的な施設名・店名が話されたときだけ入れさせる。**料理名やあいまいな言葉（「ランチ」「ホテル」）ではなく、店名・施設名を場所にする**。推測で埋めさせず、分からない項目は空にさせる。話したURL（`mapUrl`＝Googleマップ、`shopUrl`＝それ以外）は、既存の「URLやお店の名前など」欄の仕組みを引き継ぐ（URLの地図がある候補は場所検索しない）。スキーマはスクショの項目から`image`・`checkOutDate`・`placeGuessed`を除き、`mapUrl`・`shopUrl`を足したもの。
- **場所検索**：スクショと同じ`collectPlaceQueries`→`googleTextSearchOne`→`attachPlaces`（名前ごとに1回、同じ名前は1回、**最大12回**、溢れたぶんは地図なしで出して本人が探す）。`GOOGLE_API_KEY`が無いときは、音声・メモは地図なしで候補を返す（機能自体は`server_not_configured`にしない）。
- **決まった形のメモ・JSONの取り込み**（クライアントだけ）：`Core.memoBlocksToProposals`。時刻は`parseMemo`が読んだもの、費用は`Core.parseCostsFromLine`が文章から拾う（`1,500円`・`¥1500`・`＄12`・`12ドル`・`€3.5`など、お金の印が付いているものだけ。ただの数字は拾わない。見出しに書かれた金額は見出しから取り除く）。GoogleマップのURLは地図、それ以外のURLはお店のURL。**有料の場所検索は自動では走らせない**（無料の経路のため）。場所は確認画面の各候補の「場所を探す」（スクショと同じ`/places/search`・`/places/details`。探す欄の初期値は見出し）。

### 枠・取り消し・文字起こし

- 枠の消費は今までどおり：音声＝音声の枠（文字起こし〜整理が成功して候補ができたあとに1回）、メモ（AI）＝メモの枠、決まった形のメモ・JSON＝使わない。`voice-scan`・`text-scan`が候補を返した時点で1回消費し、**確認画面で取り消しても戻らない**（AIはすでに動いたため）。画面に「やめると保存されません。AIによる整理はすでに行ったため、今月の利用回数は戻りません」と書く。
- 音声の**文字起こし**は、これまでどおりその日の欄（`day_infos.voice_transcript`）に残す。ただし保存のタイミングを「AIが整理した直後」から「確認画面で追加したとき」に移した（`import-blocks`の`transcript`／`transcriptDate`）。取り消したら何も残らない（文字起こしも消える）。メモ（AI）の元の文章も、1日だけの取り込みでは従来どおり同じ欄に残す。複数日・別行動では残さない（複数日は日が決まらないため。別行動は、その日の欄がみんなに見える情報で、別行動の中身が漏れるため）。

## 2026-09-30 追記：日程の外の日付の候補を、確認画面で「日程を合わせる／日付をずらす」

**きっかけ**：`docs/adr/0015`の追記のとおり、メモに書かれた日付（5/16）が旅行の日程（12/11〜）と別だったとき、黙って日程に寄せられていた。書かれた日付は直さずに確認画面へ渡し、本人が合わせ方を選べるようにした。

**決めたこと**：
- **どの入口も、日程の外の日付のまま確認画面に届く**。メモ・自分のAIのJSON：`Core.parseImportedBlocksJson`が外の日付を残す。音声・メモ（AI）：`normalizeProposalResult`は、旅行全体の複数日モードでは日付を日程の日々に限らない（書かれた月日は日程の年で補い、外なら「旅行の日程の外の日付です」の警告）。日付が読めなかったものだけ従来どおり初日に置いて警告する。スクショは元々外の日付を残す。**別行動（自分だけの道）に入れるときは、従来どおり別行動の日々の外を信用しない**（時間帯の規則があるため）。「この日」モード（1日）も日付を固定するため従来どおり。
- 確認画面に、日程の外の候補が1件でもあるとき案内を出す（`ssDateFitBanner`。使う候補だけ数える）。ボタンは2つ。
  - **「旅行の日程を M/D〜M/D に合わせる」**（別行動への追加では出さない）。`Core.planTripRangeFit`：使う候補が**すべて日程の外で、旅行に予定がまだ無い**なら日程を候補の最初〜最後に**置き換え**、一部でも日程の中にある、または今の旅行に予定がすでにあるときは、今の日程と候補の両方が入るよう**広げる**（置き換えると、外になった今の予定が画面から見えなくなるため）。既存の旅行更新API（`PATCH /trips/:id`）に`startDate`・`endDate`だけを送り、**`shiftDays`は送らない**＝既存の予定・日ごとの情報の日付は動かない（旅行の編集画面のように「予定もずらす」確認はここでは出さない）。31日を超える日程になるときは「日付の間違いではありませんか」と確かめる。
  - **「予定の日付を旅行の日程に合わせてずらす」**：`Core.planProposalShift`／`shiftProposalDates`。使う候補のいちばん早い日が、選べる日の最初の日（旅行の1日目。別行動なら別行動の初日）になるよう、**すべての候補を同じ日数**動かす（日と日の間隔・到着日`arriveDate`も同じ。月・年またぎも日付として計算）。最後の候補が日程の終わりを越えるときは、案内の文と確認で知らせ、それでもずらせる（越えた分は日付を直す）。
- どちらのあとも、再検証する（警告は日程との比較を描くたびに数え直す。`ssWarningsOf`）。まだ外にある候補は、これまでどおり候補ごとの警告が出て、直すまで追加できない（`Core.screenshotItemsToSavePayload`）。

**避けたこと**：日程の外の日付をAIや取り込みが黙って寄せること／日程を合わせるときに、既存の予定まで勝手にずらすこと。
