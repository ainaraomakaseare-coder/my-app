# たびログ

旅行の記録を、日ごと・時間ごとのタイムラインとして家族・仲間で共有するアプリ。サーバー（データベース）に保存し、旅行のURLを知っている人だけが読み書きできる。

## 見た目の方向性

「Slack・Confluence風のモダンなSaaSツール」（薄いグレーの背景・鮮やかな青のアクセント・カードは角丸12px＋薄いぼかし影・カテゴリはConfluenceのラベルのような色付きピル）。Claude Designで作った「あたたかい編集手帳」（クリーム色・テラコッタ・明朝体・オフセット影）を一度採用したのち、「Slack・Confluenceを教科書にしたモダンな配色・図形」という指示で作り直した。
_Avoid_: テラコッタ・クリーム色・明朝体・オフセット影（1つ前の「編集手帳」方向の名残）、紫のアクセント（さらに前の「るるぶ風→Slackモダン」の名残）は、どちらも新しく足す要素には使わない

**Trip（旅行）**:
1件の旅行・イベント全体を表す最上位の単位。タイトル・出発日〜帰着日・参加者（companions）を持つ。共有はTrip単位のURL（`trip_xxxxxxxx`というIDを含む）で行う。

**Block（大項目／予定）**:
Trip内の、ある日・ある時間の「予定」。日付・時間・見出し（label：例「那覇空港に集合」）・種類（category）を持つ、いつ・どこで・何をする時間かという枠。1つ以上のEntryがぶら下がる。
_Avoid_: エピソード（Entry側の語なので、Blockを指して使わない）

**Entry（小項目／記録）**:
あるBlockのときの、一人ひとり（またはサブグループ）の記録。エピソード（episode）・ひとこと（comment）・写真・費用の明細（costItems）・待ち時間（waitTime）・地図URL（mapUrl）・お店のHP（shopUrl）・記録した人（author）を持つ。
_Avoid_: アクティビティ（宿泊・移動もEntryとして同じ形で扱うため、activityという言葉は活動系のcategoryだけを指すと誤解される）

**別行動**:
旅行中、全員が常に同じ行動とは限らないこと。仕組みとしては特別なフィールドを持たず、**同じBlockの下にEntryを複数作ることで表現する**（例：「15:00 首里城公園に到着」というBlockの下に、父チームのEntryと母チームのEntryを2つ並べる）。
_Avoid_: グループタグ／groupTag（初期の設計案で検討したが、複数Entryで表現する方式に置き換えたため使わない）

**Category（種類）**:
Blockの区分。`sightseeing`（観光）・`food`（食事）・`lodging`（宿泊）・`transport`（移動）・`other`（その他）の5つ。`lodging`だけタイムライン上で見た目を変える（宿泊として強調する）。

**費用の明細（costItems）**:
Entryが持つ、`{label, amount}` の配列。例：「そば ¥800」「飲み物 ¥400」。合計はEntryごと・Blockごと・Trip全体それぞれで自動計算する（`entryCostTotal` / `blockCostTotal` / `tripTotalCost`）。
_Avoid_: 一人当たりの費用、という言葉を「複数人の合計を割り勘した金額」の意味では使わない（Entry自体が1人またはそのサブグループの記録なので、Entryに書いた金額がそのままその人の費用になる）

**共有リンク / 招待**:
`index.html?trip=<TripのID>` の形のURL。このURLを知っていること自体が閲覧・編集の権限になる（Googleドキュメントの「リンクを知っている全員が編集可」に近い方式）。**閲覧・編集はログイン不要のまま**（下記「評価」だけが例外でログインを必須にする）。
_Avoid_: 「招待する」という言葉から実際のメール招待・アカウント制の招待を連想させないこと（実体はURLの共有のみ）

**ログイン（アカウント）**:
3つの方法がある。①Google、②Apple（クライアントID未設定ならそれぞれ非表示）、③**メール（常に使える）**：お名前とメールアドレスをその場で入力するだけで、実際にメールを送って確認することはしない。**いずれもサーバー側で検証しない、ブラウザ内だけの簡易的な本人確認**（`{name, email, provider}`をlocalStorageに保存するだけ）。ログインすると「記録した人（author）」欄に自動で名前が入る。ログインの有無に関わらず、旅行の閲覧・記録の追加自体は今までどおりリンクだけで可能（＝ログインは「本人確認」のためであり、「アクセス制御」のためではない）。
_Avoid_: ログインを、閲覧や編集そのものを制限する認証と混同しないこと。制限がかかるのは「評価・マイログ」機能だけ

**（iOS審査についてのメモ）**:
App Store Review Guideline 4.8は「第三者・ソーシャルログインを使うなら、Sign in with Appleも同格の選択肢として用意する」ことを求める。Googleログインを提供しているため、Appleでのサインインは既に用意済み（`apps/day07-tabilog-ios/README.md`参照）。③のメール欄は外部サービスへの認証委譲ではなく、サーバー検証もしないただの入力欄（実質「ニックネーム登録」に近い）なので4.8を新たに発生させるものではないと考えているが、審査で「なぜOAuthと生のメール欄が並んでいるのか」を聞かれる可能性はゼロではない。もし審査で指摘された場合は、iOS版だけメール欄を隠す・文言を「ログイン」ではなく「お名前の登録」に変えるなどの調整で対応できる。

**評価（Rating）**:
Entry（記録）に付けられる、★1〜5の評価。**カテゴリを問わずどのEntryにも付けられ、必須ではない**（付けなくてもよい）。**評価はログイン済みの本人しか付けられない**（未ログイン・自由記述のauthor欄では付けられない）。1つのEntryに、ログインした同行者それぞれが個別に評価を付けられる（例：父と母が同じEntryにそれぞれ★を付ける）。Trip全体の総合スコアは、付けられた評価の平均で出す。
_Avoid_: 「楽しかったか」という単一の軸だと誤解しないこと。実際はカテゴリに応じて「飯ログ／ほてログ／アクティビティーログ」などの意味を持つ評価軸になる（下記「マイログ」参照）

**マイログ**:
ログイン中のアカウントに紐づく、**複数のTripを横断する**新しい画面。自分が付けた評価を、Blockのcategoryに応じて「飯ログ（food）」「ほてログ（lodging）」「アクティビティーログ（sightseeing）」「移動ログ（transport）」「その他ログ（other）」に分類し、**評価が高い順・時系列順を切り替えて**一覧できる。**ログイン必須**（共有リンクでの非ログイン公開はしない。他人には見せない前提）。
_Avoid_: Tripのホーム画面にある「マイ旅行」一覧（ブラウザのlocalStorage頼りで端末ごとに別々）と混同しないこと。マイログはアカウントに紐づき、端末をまたいで同じ内容が見られる点が異なる

**（保留・未着手）権限の細分化**:
Trip・マイログを「公開／非公開／同行者だけ」のように分ける権限設計は、要望はあるが今回は着手しない。現状の「リンクを知っていれば誰でも編集可」のままで、後日あらためて要件を詰める。

**（既知の弱点）マイログのメールアドレス**:
`/mylog` はメールアドレスを渡すとその人の評価履歴（旅行名・場所・写真）が返る作りで、サーバー側でGoogle/Appleのトークンを検証していない（このアプリ全体と同じ簡易的な仕組み）。つまり、他人のメールアドレスを知っている人であれば、その人のマイログを覗けてしまう。閲覧に必要な「trip_xxxxxxxx」というランダムなIDと違い、メールアドレスは推測・入手されうる情報なので、今までの「リンクを知っていれば見られる」より一段階、情報が漏れる範囲が広い。**メールログインを追加したことで、この弱点はより顕著になった**（Google/Appleは少なくとも実在するアカウントの所有者しか名乗れないが、メールログインは他人のメールアドレスを「自分のもの」として入力するだけで、その人になりすませてしまう）。家族向けの低リスクな前提で今回はこのまま実装したが、本格的に外部公開するならGoogleのtokeninfo検証・AppleのJWKS検証を`/entries/:id/rating`と`/mylog`だけに追加する余地を残している。
